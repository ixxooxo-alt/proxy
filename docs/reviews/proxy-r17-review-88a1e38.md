## 已确认问题

### R17-F01：close_stubs 未等 DNS 接收线程结束，可能先返回成功、再记录异常

**类别：文档不符／测试工具可靠性；优先级中。不是生产配置的泄漏漏洞。**

**位置：**

- `tools/check_real_routes.py:188–199`：工作线程接收后解析，解析失败才写入 unparsed。
- `tools/check_real_routes.py:212–224`：close 只关 socket；close_stubs 随即读取 unparsed，没有等待工作线程结束。
- 同文件 `518–521`、`604–607`、`787–790`、`1183–1188`、`1273–1278` 等调用处先构造结果，再在 finally 中关闭。
- `tests/test_real_data.py:981–1000`：现有 DNS 负向测试先 sleep(0.3)，并确认 unparsed 已有内容，才关闭；没有覆盖“已接收、尚未记完”的交错。

**为什么错：** 关闭 socket 不等于接收线程已完成处理。一个查询已经被 recvfrom 交给工作线程，只是该线程还没执行到 unparsed.append，主线程便可能检查到空列表并返回成功。解析稍后结束才留下异常，调用者已失去本轮应拒绝结果的机会。

**独立复现一：控制线程交错。** 在真实 UDP 接收线程进入原解析函数前，用 Event 暂停；发送的确实是本版测试使用的截断 DNS 查询，没有改解析结果。暂停期间调用本版原始 close_stubs：

| 时点 | 结果 |
|---|---|
| 工作线程已收到查询、解析暂时暂停 | unparsed 为空 |
| 调用 close_stubs | 正常返回，工作线程仍存活 |
| 恢复原解析函数并等待线程结束 | unparsed 出现该查询 |
| 再次调用 close_stubs | 才抛出 RuntimeError |

查询字节为 `1234010000010000000000000573686f7274`。原解析器最终按截断输入处理；不是人为把合法请求改成了错误。

**独立复现二：不暂停、不修改解析器。** 在本机循环 100 次，每次启动原始 DnsStub、发送同一异常数据报后立即调用原始 close_stubs。结果：

- 1 次在返回前报错；
- **99 次返回时未报错，随后接收线程才记录该异常**；
- 0 次在观察点仍未看到该数据报。

这是本机“发送后立刻关闭”的竞争探针结果，**不是实际全套检查有 99% 漏报的统计**。实际核对通常有等待、会先停止内核；本轮没有证据证明存档日志已经因此出现错误。但固定等一小段时间不能提供线程同步保证。

**建议怎么改：**

1. 停止发送端后，明确结束采样；让 DNS 工作线程处理完已接收的请求，再汇总 seen/unparsed 并计算结果。
2. 为 DnsStub 增加可结束的接收循环、唤醒或短超时机制，并 join 工作线程。不能只加无限 join：当前阻塞的 recvfrom 未必因另一个线程调用 close 就及时退出。
3. join 超时应把本项标成未完成，不能当作诊断为空。
4. 用 Event／Barrier 写确定性的收尾回归用例，不依赖 sleep(0.3) 恰好够用。
5. 现有 close_stubs 应保留“收集全部替身的问题后统一报错”的思路；无需因此修改生产配置。

依据：[本提交 DnsStub 与 close_stubs](https://github.com/ixxooxo-alt/proxy/blob/88a1e388e38adaecdffe0e99e70e7c702169446d/tools/check_real_routes.py#L174)；[Python Thread.join 文档](https://docs.python.org/3.12/library/threading.html#threading.Thread.join)，join 等待线程结束。关键结论同时由上述原始代码运行复现支持。

**复现紧接着关闭的最小脚本**（在本提交的工程根目录运行，只访问本机）：

```python
import socket, sys
sys.path.insert(0, "tools")
import check_real_routes as c

packet = bytes.fromhex("1234010000010000000000000573686f7274")
late = 0
with socket.socket(socket.AF_INET, socket.SOCK_DGRAM) as u:
    for _ in range(100):
        st = c.DnsStub("probe", {})
        st.start()
        u.sendto(packet, ("127.0.0.1", st.port))
        reported = False
        try:
            c.close_stubs([st])
        except RuntimeError:
            reported = True
        st.join(0.015)
        late += not reported and packet.hex() in st.unparsed
        if st.is_alive():  # 仅为本探针清理仍阻塞的线程
            u.sendto(b"", ("127.0.0.1", st.port))
            st.join(0.2)
print("关闭返回后才记录异常的次数：", late)
```

观察点之后的清理唤醒包不计入上述 late 计数；判定只认最初那份异常查询的完整十六进制。线程调度不同，次数可能不同，确定性交错用例更适合作回归测试。

### SOCKS 接收端：空连接、不完整与 8 秒

本轮独立发送协议字节，主要结果如下：

| 输入 | 回复／分类 | 结果 |
|---|---|---|
| 只提供方法 02 | 05 FF；invalid +1 | 正确 |
| 未知 ATYP=09 | 05 08；invalid +1 | 正确 |
| IPv4 地址只发一字节后半关闭 | 请求不完整；invalid +1 | 正确 |
| 不支持的 BIND | 05 07；invalid +1 | 正确 |
| 握手只发 05 后关闭 | 握手不完整；invalid +1 | 正确 |
| 整个连接没有发送数据 | empty +1，invalid 不增 | 合理 |
| 完成方法协商后不发请求便关闭 | 请求不完整，不算 empty | 与按“整个连接收到的字节数”划分一致 |
| 完整 CONNECT valid.example:443 后正常关闭 | seen 记录域名；invalid 不增 | 正确 |
| 握手只发一个字节后持续等待 | 约 8.01 秒后记不完整 | 符合工具超时设置 |

先检查 VER、RSV、CMD，再检查 ATYP 并读地址，修复了 r16 静默退出的反例。对应依据为 [RFC 1928 第 3–6 节](https://www.rfc-editor.org/rfc/rfc1928)。UDP 的 RSV／FRAG／源地址与关联生命周期主要逻辑未改，完整测试中相应回归也通过。

**8 秒的性质要说清：** socket 的 timeout 是一次阻塞接收的等待限制，不是整个握手／连接从建立起总共只能持续 8 秒。慢客户端若两次数据之间超过此预算，即使最终打算发送合法报文，也会被本工具记录为不完整。这是本机核对工具的采样预算，不能据此证明对方违反 RFC。当前记录“不完整或超时”并拒绝给出可信结果，方向是保守的；无需为了掩盖超时改回静默记成未发送。后续可把 timeout 与格式错误分列，属于建议。

## 第 22 项：选项和代价

r17 的改写总体正确，保留用户决定，未自动增加 resolve 或改变出口。

- ① 已收窄为一般浏览器可能退回 TCP，没有保证网页、视频或纯 UDP 应用照常；合理。
- ② 明确本机 UDP DNS 替身验证不等于真实 dns-foreign → 代理 → DoH 全程验证；补了作用范围、可选 DIRECT、DNS 自身循环、失败、缓存、A/AAAA、回包及 TUN 成本；完整度明显改善。
- ③ 先确认 SFA 内核，再用同一最小场景和实际配置验证新版；有直接相关的源码依据，仍是合理的优先顺序。

“确定走代理之后再解析”应理解成实现必须满足的作用范围约束，不是说把 resolve 简单放到一个已经终止的 route 动作后面就会生效。现在尚未实现②，所以这不是当前配置错误；实施时需要说明具体规则匹配方式。

1.14.3 的 interrupt PacketConn 保留扩展报文接口，是上轮已经核对的源码事实；r17 正确标注其中哪些是维护者自己核对、哪些引用审核方。没有将其升级为 SFA／TUN 实测。1.12.0 的 SOCKS + urltest 例外仍应保留，不要只因 selector 对照正常就宣称所有旧版路径正常。

本轮没有重新运行完整官方内核批次，也没有重试上轮已经失败的启动来制造一个新的“UDP 失败”结论。两份 sing-box 配置与 r16 逐字节相同；原有运行限制和真实设备边界未解除。
