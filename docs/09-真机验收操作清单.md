对应统一源 2026.10.07-2 生成的配置（r14）。**r14 和上一版 r13（2026.10.06-1，配置与 r12 相同）相比，四个客户端的配置都变了，导入过 r12、r13 的要重新导入。** 这张清单里 r14 加的或改的几处标了“2026-10-07”。

- **你 2026-10-07 定下的几项**（`docs/06`“2026-10-07 你定下的事项”）：“国内直连”固定直连，组里只剩 DIRECT；对时、运营商号码认证用的 8 个名字四个客户端都固定直连；Bilibili 港澳台默认直连；友盟、阿里妈妈只拦统计 / 广告子域；Apple AI 去掉三条宽规则（地图 / 定位、App Store 图标、CloudKit 回到 Apple 组）；“Netflix·解锁入口”取消，策略组从 82 个变成 81 个；Clash 系上不带点的名字、路由器管理域名的 DNS 查询交给系统 DNS；Quantumult X 严格版多订阅一份上游国内大清单的副本。
- **处理 GPT 对 r13 的审核**：Clash 系的 DNS 多了一层——走代理的网站，名字在转发 UDP（浏览器的 HTTP/3 等）、经 WireGuard 节点时也只问境外 DNS（`docs/03` 最后一节）。
- 严格版（`loon-strict.conf`、`quantumultx-strict.conf`，r12 加的）在手机上仍然完全没有验证过，要用的话请先做下面的“1b. 严格版”。**它引用仓库 `main` 里的规则文件（Loon 一个，Quantumult X 三个），`main` 更新到这一版之前用不了**（r12、r13、r14 交付时都没有推 `main`，等你发话再推）。

还没有导入过 r12 的：r12 相对 r11（2026.10.05-2）给六份标准版加了策略组 Apple Push（Apple 的推送通知单独一组，默认直连）；加了两份严格版；Clash 系和 SFA 加了检查和一张“要手动确认的开关”清单（`docs/01`）——第 1 节多了几行。

还没有导入过 r10、r11 的，下面这些更早的改动同样适用：① r10 相对 r9（2026.10.04-2）：各地区的“自动 / 故障转移 / 负载均衡”更严了——只写“地名 + 中转”或“国旗 + 中转”、或者地区只出现在解锁说明里的节点不再进这三种组，只留在手动组；Loon、Quantumult X、Clash 系客户端的策略组各带了一个图标地址（你的图标仓库里的图）；sing-box 多一条路由规则（局域网里的名字先用系统 DNS 解析）。② r11 相对 r10：Clash 系的两份配置的 dns 段多了一个字段——服务器地址是局域网名字的节点改由系统 DNS 解析。与更早的 r7（2026.10.02-1）相比的逐条差异见 `docs/evidence/与r7的对比.md`。

手机上的 Loon、Quantumult X、SFA、Clash Meta for Android 只能你自己操作。电脑上的 Clash Verge Rev 可以用 `tools/check_connections.py` 自动判断每个连接走得对不对。

## 0. 开始之前（安全）

- 不要在正在跑 Grok bot / Cursor 调度的那台电脑上直接换配置。先确认两件事：能一键切回旧配置；就算代理完全不通，也知道怎么关掉系统代理 / TUN 恢复上网。
- 新配置用“新增配置 / 订阅”的方式导入，保留旧的，不要覆盖。
- 订阅链接只在你自己的设备上填：在电脑上用 `SUB_URLS='你的订阅' python3 build.py` 生成 `dist/private/` 里的版本，或者在客户端里把占位链接换掉。填好订阅的文件、控制接口的密钥，不要发给任何人，包括我。
- 测试期间关掉无关的网页和应用。连接记录会列出你访问过的网站，发出去之前自己先看一眼。

## 1b. 严格版（Loon / Quantumult X；r12 新增，只在你要用严格版时做）

严格版的做法见 `docs/03`“Loon / Quantumult X：严格版”一节。它在模拟器里符合预期，但两个 App 的规则先后有靠推断的地方，**下面每一步都是为了确认一个没有官方依据或没有验证过的点**，请按顺序做，哪一步不对就先切回标准版，把现象（截图最好）发回来。表格的思路来自 GPT 2026-10-06 对方案的评审。

准备：仓库的 `main` 已经更新到这一版（浏览器能打开 `https://raw.githubusercontent.com/ixxooxo-alt/proxy/main/dist/quantumultx/rules/domain-fallback.list`，看到里面只有一条规则）；新增一份配置导入严格版，不要覆盖标准版；换上订阅。测试用的域名要“新鲜”——选今天没有访问过的，App 和系统都会缓存解析结果，访问过的域名看不出有没有重新解析。每做一步之前，把 App 的连接开关关掉再打开一次，尽量清掉它记着的解析结果。

| 步骤 | 怎么做 | 通过标准 | 这一步在确认什么 |
|---|---|---|---|
| 1. 远程规则都加载了 | Loon：打开“订阅规则”。Quantumult X：打开“分流”里的引用列表。各点一次更新 | Loon 四条都更新成功：广告两条（约 370 条、三万七千多条）、“国内域名-ChinaMax”（十一万多条）、“国内域名-自有清单”（6,133 条）。Quantumult X 四条（2026-10-07 起；以前三条）：广告（三万七千多条）、“国内域名-ChinaMax”（111,182 条，仓库里的副本）、“国内域名-自有清单”（6,133 条）、“域名兜底-不在本机解析”（1 条）。条数差得多、显示 0 条、报格式错误，都算没通过 | 规则文件的格式被 App 接受；仓库里的文件取得到；Quantumult X 能加载十一万多条的远程规则（约 3.5 MB，没有查到它对大小的限制）。Quantumult X 的兜底没加载时，严格版会悄悄退回标准版的行为 |
| 2. 导入没有报错，策略组没有少 | 同第 1 节 | 81 个策略组都在；Loon 没有对 `GEOIP,CN,国内直连,no-resolve` 这一行报错 | Loon 是否接受单独一行 GEOIP 加 `no-resolve`（官方只在逻辑规则的例子里这样写过） |
| 3. 没被接住的境外域名：走代理，而且本机没有解析它 | 浏览器打开一个冷门的境外网站（规则里没有、今天没访问过的；例如随便搜一个国外小网站）。然后看 App 的请求记录；Loon 另外看“DNS 记录 / DNS 查询日志”（在哪个菜单我没有核对），Quantumult X 看请求详情里有没有解析出来的 IP、DNS 耗时 | 请求记录里这个域名命中的是 FINAL（Loon）或“域名兜底”（Quantumult X），策略是国外默认。**本机没有为它查 DNS**：Loon 的 DNS 记录里没有这个域名；Quantumult X 的请求详情里没有本地解析出来的地址。标准版上做同一件事可以看到差别（标准版会有解析记录）。DNS 记录里如果能看到查询类型，再留意一下：这个域名有没有 A / AAAA 以外的查询（例如 HTTPS，类型 65）被发给了国内 DNS——两个 App 怎么处理手机发出的这类查询，官方没有写（2026-10-07 加，`docs/03`“严格版”一节最后） | 严格版的核心：`no-resolve` / 域名兜底真的让 App 不解析。如果这里看到了解析记录，严格版没有起作用 |
| 4. DNS 泄露测试 | 打开 dnsleaktest.com 之类的网站，做一次标准测试 | 列出来的 DNS 服务器里没有国内的（阿里 223.5.5.5、腾讯 1.12.12.12 / 119.29.29.29，或者你的运营商） | 第 3 步的旁证。它只是必要检查 |
| 5. 清单里的国内网站：直连 | 打开 `www.zhihu.com`、`www.163.com`、一个 `.cn` 结尾的网站 | 请求记录里策略是“国内直连”，命中的是“国内域名-…”那条远程规则（`.cn` 的网站在 Loon 上命中的是“自有清单”） | 国内清单生效；它排在兜底之前 |
| 6. 清单里的域名下的广告主机：仍然被拦 | 打开京东或 12306 的 App / 网页，在请求记录里找被拦的请求；或者直接在浏览器里访问 `ad.12306.cn` | 广告主机命中“广告拦截”，不是“国内直连” | 远程规则之间按书写顺序：广告集合先于国内清单（官方没有专门写多条远程规则之间的先后） |
| 7. 有规则的服务：不变 | 打开 ChatGPT、YouTube，再打开 `chat.qwen.ai` | 分别进 OpenAI、YouTube、国外默认，而且和第 3 步一样没有本机的解析记录。`chat.qwen.ai` 尤其要看：上游的国内清单收了它，本地规则让它走国外默认 | 本地规则先于远程规则；同时在“国内清单”和“走代理的规则”里的域名，不会先被当成国内的 |
| 8. 原本就是 IP 的连接：不变 | Telegram 收发一条消息；访问路由器后台（192.168.x.x）；在浏览器地址栏直接输入一个国内的 IP（例如 `223.5.5.5`，打不打得开不要紧，看请求记录） | Telegram 的 IP 连接进 Telegram 组；局域网地址直连；国内 IP 走“国内直连”（Loon 上命中的是 `GEOIP,CN`） | IP 规则保留着，域名兜底没有吞掉 IP 连接（Quantumult X 官方的说法是 host 规则不匹配纯 IP 请求）；Loon 上单独一行的 `GEOIP,CN,国内直连,no-resolve` 确实在起作用 |

第 3 步是最要紧的一步：只有它能区分“严格版起作用了”和“看起来导入成功、其实和标准版一样”。两个 App 里看 DNS 记录的菜单我没有核对过，找不到时把请求详情的截图发回来，我来判断。

怎么读第 3 步的结果（GPT 评审里的提醒，我同意）：**看到了国内 DNS 的查询记录，是明确的不通过；没看到记录，不能算充分的通过**——可能是缓存、可能是这条路径没有被记下来；Quantumult X 的 DNS 记录只记第一个应答的服务器（官方 README 的说法），不代表别的服务器没有被问过。所以每次都换一个没访问过的域名，并且和标准版对照着看：标准版上有记录、严格版上没有，才说明差别是严格版带来的。要更确定，只能在路由器或电脑上抓包看手机发出了哪些 DNS 查询，这超出了这张清单的范围。

这张表没有覆盖的：国内的加密 DNS 连不上、证书出错、返回错误时两个 App 各怎么处理（Loon 的回落开关是其中一种）；IPv6 网络下的表现；你自己在 App 里另加的规则或插件（里面有不带 `no-resolve` 的 IP 规则时，Loon 严格版会为它解析没被接住的域名）；浏览器自己的安全 DNS、程序缓存了地址以后直接按 IP 连接、系统在隧道之外发出的流量（GPT 审核 r12 第 3 点列的验证边界）。

| 覆盖范围 | 分别测浏览器、命令行（例如 `curl.exe -I https://www.google.com`）、后台同步类应用 | 都受规则控制；系统代理模式下命令行可能不走代理，这时记下来 |

## 6. 写给代为检查的 AI

你的任务是读取这台电脑上 Clash Verge Rev（mihomo 内核）的连接记录，用本项目的工具判断分流是否正确，把报告交给用户。

**约束**

- 只读：不修改客户端配置，不切换配置 / 订阅 / 节点，不开关 TUN 或系统代理。需要改任何设置（例如打开外部控制器）先问用户。
- 不要执行 `DELETE /connections`，除非用户同意：它会中断所有正在进行的连接，包括下载和通话。让用户关掉浏览器或 App 再测，效果一样。
- 控制接口密钥、订阅链接、节点服务器地址不要写进报告，也不要发给任何人。交给用户的是工具生成的报告，不是原始记录。
- 需要登录账号的服务由用户自己操作。你只负责采集和分析；如果你能控制浏览器，只打开不需要登录的公开页面。
- 发现规则问题只报告，不要自己改 `source/`。用户同意改的话，按 `README.zh-CN.md`“改规则”的流程做，每条规则写明证据。

**步骤**

1. 找控制接口的地址和密钥。优先在 Clash Verge Rev 的设置里看“外部控制器”；也可以读它的运行时配置 `clash-verge.yaml` 里的 `external-controller` 和 `secret` 两行。这个文件一般在 Windows 的 `%APPDATA%\io.github.clash-verge-rev.clash-verge-rev\`、macOS 的 `~/Library/Application Support/io.github.clash-verge-rev.clash-verge-rev/`，以实际安装为准。如果外部控制器没有开，问用户是否打开（只监听 127.0.0.1，设置密钥）；用户不同意，就改用下面第 5 步的“复制日志”办法。直接运行本项目 `mihomo-core.yaml` 时，地址是 `127.0.0.1:9090`，没有密钥。
2. 确认接口能用，并记下内核版本（Windows 请用 `curl.exe`，PowerShell 里的 `curl` 是别的命令）：
   ```
   curl.exe -s -H "Authorization: Bearer <密钥>" http://127.0.0.1:<端口>/version
   ```
3. 每个服务单独采集一次。开始采集后告诉用户“现在开始用某某服务”，时间到了自动停止：
   ```
   curl.exe -sN --max-time 180 -H "Authorization: Bearer <密钥>" "http://127.0.0.1:<端口>/logs?level=info" -o netflix.jsonl
   curl.exe -s -H "Authorization: Bearer <密钥>" http://127.0.0.1:<端口>/connections -o netflix-connections.json
   ```
   第一条收集这 3 分钟里每个新连接命中的规则和组（到时间 curl 会报超时，属于正常，文件已经写好）；即使配置里 `log-level` 是 warning，这个接口也能收到。第二条是使用结束时仍在活动的连接，带进程名，用来区分浏览器和其他程序的流量。
4. 分析（在本项目目录下运行，需要 Python 3.10+ 和 PyYAML；Windows 用 `python`）：
   ```
   python3 tools/check_connections.py --service netflix netflix.jsonl netflix-connections.json --out netflix-报告.md
   ```
   退出码 1 表示有连接和统一源不一致，先确认客户端用的是这一版配置（`dist/manifest.json`）。报告里“落入国外兜底”的主机，就是可能漏掉的域名，要结合第 2 节的通过标准逐个判断。
5. 没有控制接口时：让用户在 Clash Verge Rev 的“日志”页面把级别设为 info，用完服务后全选复制，粘贴成文本文件，同样交给工具分析：`python3 tools/check_connections.py --service netflix 复制的日志.txt`。
6. 把各服务的报告、内核版本、客户端版本交给用户。
