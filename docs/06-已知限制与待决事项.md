## 各端语义差异（生成器已按各端处理，但结果不完全一致）

- **Loon / Quantumult X 的广告集合优先级低于本地产品规则**（Loon 官方：本地 > 插件 > 订阅）。domain-list-community 快照里落在产品规则范围内的 30 个广告条目，已全部前置：28 条放进自有拦截（四端都拦），2 条按 GitHub 官方放行清单放进误杀例外（四端都不拦）。blackmatrix7 的广告列表里另有 125 个域名条目落在本地产品规则的范围内（`ads.twitter.com`、`ads.google.com`、`c.paypal.com`、`cm.bilibili.com` 等，2026-10-04 按固定快照数的）：这两端本地规则优先，它们跟着产品组走，不会被拦；mihomo / sing-box 用的是另一份广告集合，里面本来就没有这些条目——所以这 125 个主机四端结果相同（都不拦），不是差异，但也说明“订阅了广告列表”不等于列表里的每一条都生效。mihomo / sing-box 严格按“例外 → 拦截 → 产品规则”执行。

- **Loon 的“手动优先”**：官方示例说 url-test / fallback 只支持节点、其他会被忽略，现行文档又说策略组支持嵌套。为此 Loon 的手动优先组在两个成员组后附带同地区节点：嵌套生效时是真正的“手动优先 → 自动兜底”；嵌套被忽略时退化为同地区顺序故障转移（不跨国、不直连）。实际是哪种，要在设备上看该组的成员列表确认。

- **Loon / Quantumult X 没有引入国内 / 国外域名大集合**：它们含宽泛关键词规则（例如 `DOMAIN-KEYWORD,jav`、`DOMAIN-SUFFIX,ms`），不符合收录要求。代价是没有命中域名规则的境外域名要先由国内 DNS 解析：国内 DNS 看得到这些域名；解析结果不是国内 IP 时走国外默认，**是国内 IP 时会直连**（境外网站用了国内 CDN 节点、解析被污染到国内地址等情况）。以前这里写的是“结果仍走国外默认”，少了这个条件（2026-10-03 审核 F06），完整说明见 `docs/03`“已知取舍”第一条。**这一条说的是标准版**；2026-10-06 起另有严格版，用的是只含域名和后缀的国内域名清单（不含关键词规则），见下面“2026-10-06（r12）”一节。
- **广告数据源各端不同**：mihomo / sing-box 用 domain-list-community 的 `category-ads-all`（真实文件里 911 条），Loon / QX 用 blackmatrix7 的 `AdvertisingLite`（2025-12-08 更新；域名 37,692 条、关键词 187 条、IP 段 187 条）。两者覆盖范围不同：同一个广告主机可能在这两端被拦、在另两端不被拦，反过来也有。`tests/cases.yaml` 里有 6 个用真实广告列表核对的用例，其中 4 个在两类客户端上结果不同（`ads.yahoo.com`、`ads.viber.com`、`t.appsflyer.com`、`user.wixsite.com`），按各端分别写了期望。Loon 版分成两个文件，见下面“2026-10-04”一节。
- **sing-box**：没有故障转移 / 负载均衡组、不能隐藏子组、不支持订阅；广告拦截是规则动作，不能在界面一键关闭；首次启动要经“国外默认”下载规则集，节点必须可用；空组用的 `block` 占位出站在 1.14 已标记弃用（v1.14.1 源码中仍可用），节点转换报告会列出哪些组没有节点；排期：1.16 发布前复查，若被移除，改为生成时去掉空组并在报告中列出受影响的默认出口。不返回 AAAA 时 fakeip 不配置 IPv6 段。
- **mihomo 旧内核**会忽略 `empty-fallback`，筛选为空的组会落到 COMPATIBLE（等同直连）。官方 wiki 已记载该字段但没有写起始版本，我也没有查证；验证过的版本只有 v1.19.31（`docs/02`“已验证的版本与依据”），请用这个版本或更新的内核，更早的版本不要假定可用。

## 2026-10-05 审核（GPT r9）后的修改与仍然存在的限制

**先说结论**

- **Clash Verge Rev / Clash Meta for Android / SFA**：配置的设计本来就是“走代理的域名不交给国内 DNS”，这一轮用官方内核把这句话核对成了固定的检查（`docs/03`“走代理的域名不交给国内 DNS”一节），并把整个国内域名集合逐条扫了一遍：绝大多数符合，查出来的例外有三类（sing-box 5 个、mihomo 364 个代表主机），如实列在下面“Clash 系 / sing-box 这一边查出来、没有改的”里。配置没有改。能不能真的做到，取决于 App 和系统里的几个开关，清单在 `docs/01`“每个客户端要手动确认的开关”——**那张表是按源码和官方文档写的，没有在 App 里验证过**。

**严格版的限制**（做法见 `docs/03`“Loon / Quantumult X：严格版”一节）

- **清单里没有的国内网站走代理**。能打开，会慢；有的网站对境外 IP 显示不同的内容，个别会拒绝访问。这是它换来“国内 DNS 看不到没列到的域名”的代价。国内网站的解析本身没有变慢：清单里的网站仍然由国内 DNS 解析、直连。
- **靠推断的地方**：Loon 单独一行的 `GEOIP,CN,策略,no-resolve`（官方只在逻辑规则的例子里把 `no-resolve` 写在 GEOIP 上）；Loon 多条订阅规则之间的先后（官方只说“按配置顺序匹配，越靠前优先级越高”）；Quantumult X 远程资源之间的先后、远程资源里的域名规则先于本地的 IP 规则（官方示例只能看出域名类规则先于 IP 类规则）。模拟器是按这些推断写的，所以模拟器通过不说明 App 里也这样。
- **Loon 严格版还依赖上游规则文件的写法**：它订阅的广告集合里有 187 条按 IP 判断的规则，是上游写的；这些规则要是不带 `no-resolve`，没被接住的域名就会为它们在本机解析。按固定快照核对，187 条全部带；每次跑官方内核核对时都会重新数（`docs/03`“严格版”一节）。上游改了写法、或者你自己在 App 里另加了不带 `no-resolve` 的 IP 规则或插件，严格版就不严了，而手机上不会有任何提示。
- **Quantumult X 的域名兜底没有加载时，严格版悄悄退回标准版的行为**，没有任何提示。兜底是一个远程规则文件，取不到（仓库没更新、网络不通、文件被改名）就不存在。每次更新配置以后看一眼“分流”里的引用是不是都更新成功。
- **依赖你的仓库**：三个规则文件在 `ixxooxo-alt/proxy` 的 `main` 分支。仓库改成私有、文件改名或删除，Loon 严格版会少一份清单（整段 `.cn` 等不再认得），Quantumult X 严格版会失去清单和兜底。

- **不带点的主机名**（`http://nas/`）在 Quantumult X 严格版里接不住，仍按标准版的办法处理。
- **严格版和标准版去向不同的地方**，除了“没列到的域名”，还有三处：`time.apple.com`、`time.windows.com`、`pool.ntp.org` 等“要真实地址的名单”固定直连（标准版里前两个跟着 Apple、Microsoft 组）；`id6.me`、`log.cmpassport.com` 不再被广告集合拦（待决事项第 18 项）；清单里有、但解析到境外 CDN 的国内网站直连（标准版里走代理）。

- **没被接住的域名由代理那一端解析**，用的是节点所在位置的 DNS，由机场决定，配置管不到，也看不到。
- 十一万条（Loon）/ 六千条（Quantumult X）远程规则在手机上的加载时间、内存、耗电，没有实测。
- 上游大清单（Loon 订阅的 `ChinaMax_Domain.list`）的内容跟着上游变：哪天它收了一个本项目没有规则、你又希望走代理的域名，那个域名在 Loon 严格版里会直连。mihomo 用的国内域名集合和它的内容几乎相同（十一万条里只差几百条，`docs/03`），是同一类风险。

**Clash 系 / sing-box 这一边查出来、没有改的**（都列成了待决事项）

**核对本身的边界**

- 官方内核的核对用的是本机的代理端口和临时的 DNS 端口，不是虚拟网卡；三类 DNS 是本机替身。系统在虚拟网卡之外自己发出的 DNS 查询、浏览器自己的安全 DNS，这些核对都看不到——它们归 `docs/01` 那张开关清单管。
- “境外 DNS 不应答时不回落”只在替身上验证过：替身只收不答，连接保持 14 秒。真实网络里 DoH 连接建立失败、被重置、返回错误码等别的失败方式没有逐一试。
- 逐条扫描（r12 时叫“全集一致性”）扫的是代表主机（条目本身和它的一个子域），正则条目没有扫；判断用模拟器，官方内核核对的是其中走代理组的全部和抽出来的 200 个。扫出来的个数只对这份快照和这种取法成立，它也不是“全部域名”的证明（2026-10-07 按 GPT 审核改了名字和说法）。
- Loon / Quantumult X 没有可以在电脑上运行的官方内核，它们的全部结论来自按官方文档写的模拟器。

**Apple Push**

- 规则只有 `push.apple.com` 一条后缀，依据是 Apple 的企业网络要求（推送通知：`*.push.apple.com`，TCP 443、80、5223、2197）。同一份文档建议放行整个 `17.0.0.0/8`，那是整个 Apple 的地址段，没有按它写规则——按 IP 直接连过去、看不到域名的推送连接（如果有）不会进这个组，会按国内 / 国外 IP 规则走。

- 组选直连时，这些域名由国内 DNS 解析（和 Apple 组一样）。
- 推送服务器的 DNS 别名（`push-apple.com.akadns.net` 等三个，GPT 2026-10-07 补充提的）没有写成规则：客户端分流时看的是程序请求的原始名字，不是 DNS 应答里的别名（mihomo、sing-box 按源码；Loon / Quantumult X 是推断），这三条写进去也碰不到。真机的请求记录里出现了这些名字再加（`docs/08` 第 8 轮最后一节）。
- 图标是你选定的蓝色铃铛那一张，2026-10-06 14:12 已经传到图标仓库，核对过文件在、尺寸对；和别的图标一样，App 里显示不显示没有在真机上看过。图标仓库自己公布的地址清单（`icon-urls.json`）没有收这一张，所以这一个地址只核对了文件，没有和清单比（`docs/02`“策略组图标”）。

**没有做的**

## 2026-10-07（r13）：处理 GPT 对 r12 的审核时新写明的限制

逐条的核实与处理见 `docs/08-外部审核记录.md` 第 8 轮。**这一版的配置与 r12 逐字节相同**，下面几条都是原来就有的情况，这一轮核实时才查清或写准，没有哪一条是这一轮引入的。

- **“系统 DNS”不一定是你家路由器**（GPT 第 11 点提醒；我读 mihomo v1.19.31 的源码查清的，没有在真实系统上验证）。Clash 系的配置把局域网里的名字（`nas.lan` 这类访问目标、服务器是局域网名字的节点）交给 `system`。内核从系统设置里读 DNS：Windows 读网卡上设的，macOS 读 `/etc/resolv.conf`，Clash Meta for Android 由 App 告诉它；读不到时这次解析失败，不会改问别的服务器（**更正**：r13 这里写的是“读不到时用内置的 114.114.114.114 和 8.8.8.8”，读错了源码——那两个地址只属于内核另建的一个全局解析器，配置里写的 `system` 不带这个兜底；GPT 审核 r13 的 R13-F02，见下面 r14 一节）。两种情况下它不是路由器：
  - **Mac 上开着 Clash Verge Rev 的虚拟网卡**：App 把系统 DNS 改成了 114.114.114.114，内核的“系统 DNS”也就是它。按源码推断，这时用名字访问局域网设备、用局域网名字的节点都会解析不到，这些名字也会被发给这个公共 DNS。
  - **Windows 上照 `docs/01` 的那句建议，不开严格路由、把网卡的 DNS 改成公网地址**：同上。
  用 IP 地址访问不受影响；机场订阅的节点不受影响。怎么看：`docs/09` 第 1 节“局域网”一行。配置文件里改不了（不知道你家路由器的地址），遇到了告诉我再商量办法（`docs/03`“客户端这一侧”）。
- **Clash Verge Rev 开虚拟网卡、App 的 IPv6 开关开着时，AAAA 查询会拿到假的 IPv6 地址**（GPT 第 4 点；官方内核试过）：App 自己补了一段 `2001:2::` 开头的假地址，电脑有公网 IPv6 时内核就用它。查询仍然不交给任何 DNS，所以不影响“走代理的域名不让国内 DNS 看到”；文档里“AAAA 是空应答”都只指交付的原始配置。`docs/01` 开关表本来就建议把这个开关关掉。
- **Clash Verge Rev 的严格路由**：以前写“写在配置文件里不起作用，只能在 App 里开”，太绝对（GPT 第 6 点）。准确的说法是：在 App 里开，开完在运行时配置里确认 `tun.strict-route` 是 `true`。它管的是发往 53 端口的查询，不是所有 DNS。

- **“境外 DNS 不应答时不回落”只试了“只收不答”一种失败方式**（GPT 第 5 点）。以前 `docs/03` 写成“境外 DNS 连不上时”，说宽了，已收窄。
- **逐条扫描（r12 叫“全集一致性”）是按代表主机扫的**（GPT 第 4 点）：查出来的 5、142、222 个是这份快照、这种取法下的代表主机数，不是实际受影响的主机有多少，也不是“全部域名”的证明。（r14 起 mihomo 的 142 个那一类没有了，见下一节。）

## 2026-10-07（r14）：处理 GPT 对 r13 的审核之后

逐条的核实与处理见 `docs/08-外部审核记录.md` 第 9 轮。r14 改了 mihomo 的两份配置（`nameserver-policy` 加了一层），别的客户端的配置只有文件头上的版本号变了。

- **改了的**：mihomo 上，上游国内域名集合收了、规则又交给代理组的域名（`qwen.ai` 等，待决事项第 16 项），现在只问境外 DNS——包括转发 UDP、经 WireGuard 这类出口时内核在本机做的那次解析（`docs/03` 最后一节）。
- **改了以后的代价**：这些名字所在的组你手动切成直连时，它们也由境外 DNS 解析，可能连到离你远的服务器、变慢（sing-box 一直是这样）。默认状态下不影响国内网站。
- **仍然会让国内 DNS 看到名字的情况**（都是原来就有的）：
  - 默认直连的组（Apple、Apple Music/TV、Apple Push）你手动切到代理以后：名字仍按国内域名集合交给国内 DNS，转发 UDP、经 WireGuard 时会被国内 DNS 看到。DNS 不跟着组的选择变（和第 17 项同一类）。
  - sing-box 用 WireGuard 端点时，“要真实地址的名单”里路由走代理组的那几个名字（`time.windows.com` 等）交给 `dns-cn`（第 15 项；官方内核实测）。
  - 上游 `private` 集合里的名字（第 14 项）。
- **Loon、Quantumult X 转发 UDP 时会不会在本机解析目标域名，不知道**：官方文档没有写，也没有能运行的内核。
- **核对工具的两处修正**：读 DNS 应答时，“几个标签 + 压缩指针”这种合法的名字以前读错（R13-F04），修了，读不懂的应答现在记 `unparsed`；逐条扫描以前按“第一条命中”模拟 `nameserver-policy`，和 mihomo 不同（mihomo 不看先后，越具体越优先），改成按 mihomo 的域名树算。以前的结论不受这两处影响（当时的应答和策略里都没有这种情况）；r14 的配置里有互相包含的写法，但更具体的恰好写在前面，旧办法算出来也一样（`handoff/notes/r14_policy_order.out`），改它是为了不依赖先后。
- **说法的更正**：`system` 读不到系统 DNS 时没有 114.114.114.114 / 8.8.8.8 兜底（R13-F02）；Quantumult X 严格版比 Loon 多走代理的是 105,317 条，不是 105,446 条（R13-F03，第 19 项）。

## 节点按名称分地区：做法与限制（2026-10-02；2026-10-04、2026-10-05 更新）

规则、依据和核对结果见 `docs/02`“节点名称分地区”；怎么检查、怎么补见 `docs/01`。和使用直接相关的：

- **只看名字**：判断的是“名字写的是哪里”，不是节点实际从哪里出去。机场把名字写错、或者同一个名字换了落地，这里发现不了；实际出口仍要实测登记（`docs/05`）。所以“自动 / 故障转移 / 负载均衡只在同一个地区里切换”说的是“只在名字指向这个地区的节点里切换”，不是出口地理位置的保证。
- **Loon、Quantumult X 上没有验证过**（最要紧的一条）：地区筛选正则在 r6 是每条几百字节，r7 约 10 KB，r8 起各版（含这一版）都是 12–16 KB，而且每个地区从一条变成两条（Loon 配置 r6 → r7 → r9 → r10 和这一版：55 → 126 → 240 → 240 KB；Quantumult X 51 → 326 → 430 → 403 KB，因为它没有引用机制，26 个策略各写一遍；最长的一行约 15.8 KB）。r10 起每个策略组的行尾还多了一个图标地址。这些正则在 ICU 正则引擎上跑过、结果与期望一致，但“这两个 App 用的是 ICU”是推断，App 自己对一行的长度、对这些写法有没有限制也不知道。导入后请先按 `docs/09` 第 1 节看地区组里的节点对不对；有问题先切回 r6 的配置（统一源 2026.09.30-1，短正则），再告诉我现象。如果确认是正则太长造成的，光删少用的城市帮助有限（r7 时试过：把美国和其他国家的词表都砍到只剩几个，每条仍有 3–5 KB，因为国旗、中转这些判断本身就占一半）；那时需要给这两个 App 另出一套短写法（只做“名字里有这些词”的简单匹配，不处理中转和解锁说明），这一版没有做——审核方的意见也是“没有必要在尚未发现实际问题时全面改写”。
- **Quantumult X 的“自动”“负载均衡”**：官方 `sample.conf` 的注释说 `server-tag-regex` 只对 static、available、round-robin 三种策略生效，同一文件的示例又把它写在 dest-hash 和 url-latency-benchmark 上。本项目的“X·自动”用 url-latency-benchmark、“X·负载均衡”用 dest-hash（一直是这样）。如果注释是对的，这两个组里不会按地区取到节点。要在设备上看这两个组的成员确认；确认不生效时，这两种模式在 Quantumult X 上需要换实现或去掉。
- **说不清落地的名字只进手动组**（2026-10-04，你的决定）：例如 `日本-美国 01`、`🇯🇵 Tokyo 01 🇺🇸`、`美国 奥克兰 01`、`香港-东京 01`；2026-10-05 起还包括名字里提到的地区不在落地位置的——`日本中转 01`、`香港-中转-01`、`IEPL 01 Unlock US`、`Premium 01 | 解锁美国`（审核 r9 的 F01；上表第 12 项），以及自查补的 `🇯🇵中转 01`、`IEPL 01 🇺🇸解锁`、`香港·中转·01`、`via-HK-01`、`经香港 01`、`港日中转 01`。它们在所列地区的“手动”组里都能选到，但不进任何地区的“自动 / 故障转移 / 负载均衡”。代价：如果你的机场大量用这类写法，自动组里的节点会比手动组少——检查工具会把它们列在“说不清落地，只进手动组”里，确定落地的在 `local.yaml` 的 `node_names.assign` 里指定，指定后两边都进。
- **香港让位是一个取舍**：`香港-日本 01`、`深港专线 东京 01`、`港美 IEPL` 归对方，因为香港在这类名字里多半是中转。三种情况会分错或说不清：先写落地、后写入口又不带“中转”字样（落地香港的 `日本-香港 01` 会归日本）；名字里是“香港 / HK”加别的地区的城市（`香港-东京 01`、`HK-Tokyo 01`）——城市词也可能只是宣传语里的字眼（`香港 01 纽约时报`），所以这种一律按说不清处理，两边都只进手动组；宣传语里带着别的地区的国旗、又没有“解锁”字样（`🇭🇰 香港 01 | NF 🇺🇸`）——两面旗都在落地位置，香港让位，归美国，手动、自动都进。这种名字用 `assign` 指定。
- **没有收的写法会进“其他地区”**：单个字的简称（日、美、韩、台、新）、`LA`、`SEA`、`SJ`、紧挨着字母的代码（`HKIPLC01`）、其他国家只写两三位代码（`DE-01` 本来就该进其他地区）。“其他地区”是纯手动组，这些节点不会被自动模式用到，但也不会丢；检查工具会列出来。
- **已知会分错的 9 种写法**（如实记在 `tests/node_names.yaml` 的 `known_limits`，测试会检查“现在确实是这个结果”，规则改对了要把条目挪走）：

  | 名字 | 本来的意思 | 现在的结果 | 原因 |
  |---|---|---|---|
  | `港转美 01` | 美国 | 香港 | 认得“港”在中转位置，认不出单个字的“美” |
  | `HKIPLC01` | 香港 | 其他地区 | 代码紧挨着别的英文字母 |
  | `LA-01` | 美国 | 其他地区 | LA 也指老挝，没有收 |
  | `美 01` | 美国 | 其他地区 | 不收单个字的简称 |
  | `日本-香港 01` | 香港（也可能本来就是日本） | 日本 | 先写落地、后写入口又不带“中转”字样 |
  | `官网 hk.example.com` | 提示行 | 香港（手动、自动都进） | 提示行不带冒号、域名里又有地区代码。它测速不通，不会被自动模式选中，只是列表里多一行 |
  | `频道：@abc \| 香港 01` | 香港 | 不进任何组 | 真节点把“词 + 冒号”写在最前面，被当成提示行 |
  | `香港 01 \| 解锁 美国 \| 日本` | 香港 | 日本 | 解锁说明里用竖线分隔地区：竖线之后的不再算说明 |
  | `香港 01 支持美国流媒体` | 香港 | 美国 | 宣传语里的国名不带“解锁”字样：香港对国名一级的词照样让位 |

  遇到时用 `assign` 指定，或把写法告诉我。
- **认不出的中转写法会进自动类的组**（2026-10-05 自查时试出来的 7 种，如实记在 `tests/node_names.yaml` 的 `known_auto_limits`，测试会检查“现在确实是这个结果”）。这些名字没说清落地，按规则本该只进手动组：

  | 名字 | 现在的结果 | 原因 |
  |---|---|---|
  | `经由日本 01` | 日本（手动、自动都进） | 只认 `via` / `经` 紧挨着地名（中间最多一个空格、连字符、下划线）；“经由”多一个字 |
  | `via South Korea 01` | 韩国（手动、自动都进） | `via` 和地名之间隔着别的词。`via North Korea 01` 同理，也进韩国 |
  | `经深港 01` | 香港（手动、自动都进） | “经”和“港”之间隔着别的字 |
  | `香港跳板 01` | 香港（手动、自动都进） | “跳板”不在中转词里（同类：前置、接入） |
  | `Singapore Entry 01` | 新加坡（手动、自动都进） | Entry 不在中转词里（同类：Ingress、Forward） |
  | `日本~中转~01` | 日本（手动、自动都进） | 波浪号不在认得的连接符里（冒号、加号等也不在） |
  | `HK-JP Relay 01` | 香港（手动、自动都进） | 两个地名连着写、后面再接中转词：只有紧挨着中转词的那个按中转算，前面那个按落地算。如果本意是“香港进、日本出的中转线路”，就分错了 |

  它们和上一张表不一样的地方：检查工具不会把这些节点列进“需要你看一眼”的清单，因为在它看来这就是一个普通的落地节点。发现各地区“自动”组里有不该在的节点时，把名字告诉我；临时的办法是用 `assign` 指定。
- **同名地**：`San Jose` 按美国算（哥斯达黎加首都同名）、`Newark` / `Portland` / `Columbus` 按美国算；`奥克兰`、`圣地亚哥`、`Georgia`、`Vancouver` 因为歧义没有收进美国——名字里同时有“美国 / US”时按美国算，但只进手动组（`美国 奥克兰 01`）。
- **提示行的识别**（2026-10-04 收窄）：面板固定写法（`剩余流量`、`套餐到期` 等）、“词 + 冒号”开头、或者有提示词而整个名字没有任何地区字样，三种才算（`docs/02`“怎样才算提示行”）。两个方向都还会错：机场自创的提示行带地区字样、又不是“词 + 冒号”开头，会被当成节点（上表第 6 行）；真节点把“词 + 冒号”写在最前面，会被当成提示行（上表第 7 行）。检查工具把“当成提示行”和“有提示词但按节点处理”的都单独列出来。
- **样本不是真实订阅**：625 个带期望的节点名是我按常见写法归纳、针对规则边界写的，以及审核方构造的反例，另有 CLDR / 时区库的独立名称；它们不对应任何一家机场。等你发来更多机场的节点名（截图或文本，只要名字），我用检查工具核对后再补词表。
- **Clash Verge Rev / Clash Meta for Android**：配置里用了 YAML 的锚点 / 别名（同一条正则只写一次）。mihomo 内核读取和实际分组已验证；客户端界面层自己处理配置（合并、脚本）时是否原样保留没有验证，锚点 / 别名是 YAML 标准写法。
- **手机上的耗时是估算**：这台机器上 300 个节点 Loon 约 36–38 毫秒、Quantumult X 约 63–66 毫秒（ICU，含调用开销；2026-10-05 几次运行的范围），手机会慢几倍；没有实测。
- **很长的节点名**：几百个字符的名字也按同样的规则判断，不会卡死；匹配时间随长度大致按平方增长（Linux 上的 ICU：专门构造的怪名字，400 个字符最慢约 20 毫秒，1600 个字符约 0.3 秒，3200 个字符约 1.0 秒）。正常的节点名只有几十个字符。Loon / Quantumult X 自己对超长名字、超长正则有没有别的限制不知道。
