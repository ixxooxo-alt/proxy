## 2. 已确认的问题

### F01 · P1 · HTTP / AnyTLS 节点转换会生成不合法的 sing-box 字段

- **位置：** `generator/nodes.py:120–123`，以及 HTTP、AnyTLS 分支调用 `_dial()` 的位置（311、334 行）。
- **事实：** `_dial()` 在 `udp` 缺省/false 时统一写入 `network: tcp`，但目标版本的 HTTP 和 AnyTLS 出站没有这个字段。一个普通 HTTP 节点，或未写 `udp: true` 的 AnyTLS 节点，就能触发问题。
- **复现：** 转换报告为空，节点被视为转换成功；sing-box 1.14.1 检查整份生成配置失败：`outbounds[64].network: json: unknown field "network"`。两个协议均已复现；SOCKS5 同类样本通过，说明不能一刀切删除所有协议的字段。
- **影响：** 一条此类节点足以让整份私密配置无法通过解析；公开模板没有节点，所以现有模板检查发现不了。
- **修复建议：** 按出站协议声明可用字段与 UDP 能力。无法等价表达“禁止 UDP”的协议应明确报告/拒绝该转换，不能为了通过解析直接删约束。
- **验收：** 每个支持协议至少一个正常样本和一个缺省/false UDP 样本，生成后交给目标版本官方检查；失败不能作为成功节点交付。
- **依据：** [HTTP 选项源码](https://github.com/SagerNet/sing-box/blob/v1.14.1/option/http.go)、[AnyTLS 选项源码](https://github.com/SagerNet/sing-box/blob/v1.14.1/option/anytls.go)；本地 `protocol-http`、`protocol-anytls` 复现。

### F02 · P1 · 订阅节点名与生成器的组名没有隔离

- **位置：** `generator/nodes.py:358–368`；`generator/emit_singbox.py:83,120–123`。
- **事实：** 转换器只检查订阅节点彼此重名，没有检查节点与策略组、`DIRECT`、`无可用节点` 的冲突。
- **复现：** 分别给一个有效 SS 节点命名为“日本”“DIRECT”“无可用节点”，转换均未报告问题；官方检查全部失败，报 `duplicate outbound/endpoint tag`。
- **影响：** 节点名称是外部输入，不能假设机场一定带编号；以后新增策略组也可能与旧节点撞名。
- **修复建议：** 为节点分配独立内部标识，保存显示名映射；最低限度在写出前检查所有最终 tag 的唯一性并中止生成。固定 PayPal/Netflix 的名称引用要一起重映射。
- **验收：** 三个已复现名称，以及全部业务组/地区子组名称，都不能产生重名出站。
- **依据：** 本地 `collision-*` 配置和官方检查错误。

### F03 · P1 · 节点转换并非始终保留协议语义，存在静默丢参

- **位置：** `generator/nodes.py:67–72,167–189`。
- **最明确的事实：** 输入 `plugin: v2ray-plugin`、`plugin-opts.mux: false`，转换器因 `if opts.get("mux")` 不成立而省略 `mux`；sing-box 1.14.1 的插件实现对缺省 mux 取 **1**。因此明确关闭的复用被重新开启。
- **其他复现：** HTTP Upgrade 分支提前返回，只保留 Host/path，丢失其余 header 和 early-data 参数；`plugin-opts` 内的未知参数也没有像顶层参数那样检查，报告仍为空。缺省 Host 在两个内核中的值也不同，不能简单用“都省略”证明等效。
- **影响判断：** mux false→true 是已确认语义改变，是否导致连接失败取决于服务端配置；额外头丢失可能使需要该头的服务端拒绝握手，后者未做真实服务端通信测试。
- **修复建议：** 对每个嵌套参数建立“映射 / 明确无效 / 无法支持则拒绝”的表；显式写出 `mux=0`；对不支持的 headers/early-data 必须报告并跳过节点，不能悄悄忽略。
- **验收：** 同时测试缺省、true、false、未知嵌套键；不要只比较 JSON 字段名，须比较默认值和传输语义。
- **依据：** [sing-box 插件实现](https://github.com/SagerNet/sing-box/blob/v1.14.1/transport/sip003/v2ray.go#L78)、[mihomo 插件实现](https://github.com/MetaCubeX/mihomo/blob/v1.19.31/adapter/outbound/shadowsocks.go#L333)；`mux-false-lost`、`ignored-upgrade-options`、`ignored-plugin-option`。

### F04 · P1 · mihomo 的局域网域名直连规则缺少对应的本地 DNS 路径

- **位置：** `generator/emit_mihomo.py:175–185`；`docs/03-DNS决策表.md:10`。
- **事实：** `.lan/.local/.home.arpa` 被排除 fake-ip 并设为 DIRECT，但 `geosite:cn,private` 被交给公共 DoH，`direct-nameserver` 也是公共 DoH；没有局域网后缀指向系统/路由器 DNS 的策略。
- **影响：** 对仅由路由器/公司 DNS 知道、且本机 hosts 没有记录的名称，公共 DNS 无法提供正确内网地址。此时 DIRECT 规则并不能解决“先解析到哪里”的问题，还可能把内部名称发给公共解析服务。是否在你的 NAS/公司网络出现，需要当地网络实测；配置缺失本身已确认。
- **修复建议：** 将本地后缀与公司自定义域名显式绑定系统或指定内网 DNS；同时处理 `direct-nameserver-follow-policy`，避免直连解析绕过新增策略。确认系统 DNS 没有指回当前代理，防止循环。`.local` 的 mDNS 行为须单独验收，不能笼统保证所有本地名字均可解析。
- **验收：** 路由器 DNS 独有的测试主机可解析和访问；公共 DoH 不收到该名称；公司自定义域名的覆盖规则同时生成 DNS 决策。
- **依据：** [mihomo DNS 官方说明](https://wiki.metacubex.one/config/dns/#direct-nameserver-follow-policy)：fake-ip-filter、解析服务器选择和 DIRECT 出站解析是不同设置；跟随 policy 的开关默认关闭。

### F05 · P1（使用相关 API 时）· 将 graph.instagram.com 统一解释为统计上报不成立

- **位置：** `source/adblock.yaml:93`；`docs/06-已知限制与待决事项.md:24`。
- **事实：** 当前四端都会前置拦截该后缀。Meta 自己维护的 Instagram API 集合使用 `graph.instagram.com/.../messages` 发送消息；它不是仅有广告统计用途的主机。
- **影响边界：** 会阻断通过这台主机调用的正常 Instagram API，包括对应消息接口；没有依据断言“所有 Instagram App 的私信都会失败”。是否使用这些 API 应由业务场景决定。
- **修复建议：** 默认以正常服务功能优先，移出无条件拦截并为上游广告集合设置显式放行；如果要保留激进拦截，应放到可选档位并准确标注代价。
- **验收：** 使用该主机的正常 API 路由到 Meta 社交；上游仍标 ads 时也不得重新压过本地例外。
- **依据：** [Meta 官方 Postman：Instagram Text Message](https://www.postman.com/meta/instagram/request/1rgmhuk/text-message)。官方开发站直取本轮返回 429，因此使用 Meta 官方维护的接口集合，而非第三方教程作为证据。

### F06 · P2 · 文档建议“加误杀例外”的修复办法会被生成器拒绝

- **位置：** `docs/06-已知限制与待决事项.md:24`；`generator/model.py:423–426`。
- **事实：** 文档建议 GA/相关功能异常时加例外；但是这些域名已在自有拦截内，模型禁止任何例外与自有拦截存在包含/相交关系。
- **复现：** 添加 `graph.instagram.com` 精确例外后，直接报“例外 graph.instagram.com 与自有拦截条目 graph.instagram.com 冲突”。`analytics.google.com` 同类问题也由相同分支造成。
- **修复建议：** 选择明确语义：允许带原因和覆盖标志的高优先级例外，或要求先删对应自有拦截并同步修改文档。前者更符合“例外先于拦截”的整体模型，但需要保留意外宽放行检查。
- **验收：** 文档中的一条操作能实际恢复功能；宽泛例外仍须防止遮挡其他业务。
- **依据：** `cannot-allow-local-ad` 复现。不是否认冲突检查的价值，而是目前文档和校验规则互相矛盾。

### F07 · P1 · 发布更新没有实现“失败保留完整旧版本”

- **位置：** `build.py:94–102,137–154,174`；`docs/01-导入、更新、诊断与回滚.md` 的“更新”第 2 项。
- **事实 1：** 先写公开文件，之后才读取/下载私密节点。节点文件不存在或后续转换失败时，公开目录已变新，旧私密文件仍保留。
- **事实 2：** `os.replace()` 只原子替换一个文件。独立注入第二次写入失败后，结果为 `one.txt=NEW`、`two.txt=OLD`，整个发布目录并不具有原子性。
- **影响：** 与文档“不会出现半新半旧”及需求“更新失败保留上一份有效产物”的保证不符。失败返回码本身不能恢复已经替换的文件。
- **修复建议：** 先在独立候选目录生成公开+私密配置、审计资料和 manifest，完成所有检查后，以版本目录加一个 current 指针进行发布；失败保留旧 current，并清楚标识候选失败。不要只把 try/except 包在逐文件写入外面。
- **验收：** 订阅下载失败、节点文件损坏、官方校验失败、任一写入失败，均不改变上一份完整可用发布。
- **依据：** `transaction-failure`、`atomic-write-failure`；全部在新建的审核测试目录复现。

### F08 · P1 · run_checks.sh 遇到测试失败仍向外返回成功

- **位置：** `tools/run_checks.sh:6,17–20,27–30,43–46,54–57`。
- **事实：** 脚本只有 `set -u`；测试返回值仅通过 echo 写日志，没有向脚本/CI 传播。后面的 echo/tail/if 可以把整体退出状态变为 0。
- **复现：** 对脚本副本注入测试返回码 **7**，日志确实写“退出码：7”，但外层结果为 **WRAPPER_EXIT_CODE=0**。
- **影响：** 任何只看脚本退出码的自动化、下游代理或发布步骤，都可能把失败当作成功。这不意味着原有 58 个测试是假通过；本轮它们实际是通过的。
- **修复建议：** 每步保留真实状态并累计失败；完成日志落盘后明确非零退出。若选择遇错即停，也必须在退出前保存日志。不能只添加 `set -e` 后假定所有重定向/组合命令都正确。
- **验收：** 单测、字段核对、证据核对任一步人为失败，外层脚本均非零；成功基线仍为 0。
- **依据：** `evidence/check-wrapper.log` 与 `repro-check-wrapper.sh`。

### F09 · P2 · build 的输入校验弱于测试中的结构校验

- **位置：** `generator/model.py:189–205,265–277,406–433`；`build.py:114–137`。

- **修复建议：** 服务规则、广告、例外采用统一的严格 schema；在写盘前校验全图唯一性、引用完整性、环、客户端投影、CIDR/域名格式、模式依赖和正则编译。YAML 重复键、未知键也应拒绝，避免拼错字段被默默忽略。
- **验收：** 已复现三种输入在输出目录改变前失败，并指出源位置。
- **依据：** `invalid-ad-host`、`unknown-exception-target`、`group-cycle`。

### F10 · P2 · 版本证明链没有被完整校验

- **位置：** `build.py:63–79,127–128`；`tests/test_structure.py` 的 `test_dist_matches_source`。
- **事实：** `--check` 和相应测试主动跳过 manifest。把候选目录 manifest 改成错误版本号和空 outputs 后，`--check` 仍输出“产物与统一源一致”、退出 0。源码摘要只遍历 source/generator，未纳入实际控制生成/发布过程的 `build.py`。
- **影响：** 不能只凭该检查保证版本号、源摘要和产物 hash 均正确；当前 ZIP 的原 manifest 已由本轮另行验证，确实匹配。
- **修复建议：** 检查 manifest 的生成器/源版本、产物集合和内容 hash；将 build.py 纳入构建身份，另记录 Python/PyYAML、目标内核版本与动态规则版本。把公共源摘要和私密覆盖摘要分开。
- **验收：** 任改 manifest 一个版本/hash、遗漏一个产物或改动 build.py，相关检查能识别。
- **依据：** `manifest-not-checked` 和 `original-manifest`，两者结论不同，不应混淆。

### F11 · P2 · local.yaml 的个人信息会流入标为“公开可分享”的产物

- **位置：** `source/local.example.yaml:1–5`；`generator/model.py:159–181`；`build.py:114–120,137`；README 的目录说明。
- **事实：** local.yaml 在加载唯一模型时就被合并；公开产物也使用这个模型。独立样本中的公司域名出现在全部六份公开配置，固定节点名也出现在多份配置/正则/注释。
- **影响边界：** 本轮没有发现真实订阅密码从私密输出进入公开模板；这里指出的是公司内部域名、个人节点标识等资料，以及“local 不分享但 dist 可分享”的承诺不一致。
- **修复建议：** 构建不含 local.yaml 的公共模型，再构建含个人覆盖的私密模型；或把所有应用 local 覆盖后的文件归入 private，不再标为公开。配套添加排除规则/打包允许清单，防止以后整体压缩 dist/private。
- **验收：** 使用公司域名和固定节点名标记样本：public 内均不存在，private 按需存在。
- **依据：** `local-data-public`；本地样本均为虚构。

### F12 · P2 · 缺少必填凭据可以被算作成功转换

- **位置：** `generator/nodes.py:165,234,275,299` 等 `str(_take(...))` 调用。
- **事实：** 缺失 password 得到 None 后被转成字符串 `"None"`，节点进入成功列表，转换报告为空。SS 样本已复现。
- **影响：** 配置可能能解析但认证永远失败；成功节点数量会误导用户，也与“缺字段必须报告”的预期不符。
- **修复建议：** 必填字段先检查存在、类型、非空，再做转换；区分“缺失”和协议允许的空值。数组里非字典项、非数字端口等也要逐条报告，避免单个坏项中断整个转换。
- **验收：** 每种支持协议的必填项逐个缺失，必须进入失败报告，不输出伪凭据。
- **依据：** `missing-password`。

## 3. 已有取舍的复核意见

### 3.1 Apple AI：顺序实现符合指定基线，但名称不能证明功能已齐全

**事实：** 基线 17 条保留，关键词 siri 替换为三条后缀，共 20 条；六份产物均在 Apple 普通规则前。普通 apple.com/icloud.com 和 siriusxm.com 的回归检查通过；apple-dns.net 仍保留。没有必要为凑“18”再删两条。

**判断：** 这证明“指定迁入基线已实现”，不能证明“当前全部 Apple 智能端点均覆盖”，也不能保证换成美国节点即可使用 Apple 智能。现有说明已承认地区/设备需要真机验证，应保留这个边界。地图、商店图片、CloudKit 被一起代理的代价已记录，不重复算新错误。

### 3.2 国内 70 条只进入 mihomo/sing-box：是可解释的过渡方案

本地宽规则可能遮挡 Loon/QX 远程广告，这一设计理由合理；但 GEOIP 兜底不能保证国内服务的所有海外 CDN 主机都直连。原文已说明差异，应保持“部分实现”。

更好的候选方案是：从同一份锁定广告集合计算与产品/国内根域相交的条目，先审查误伤，再只把必要的相交项前置到本地，最后放国内根域规则。不要为了四端表面一致，继续自动迁入未经业务确认的功能域名拦截，F05 就是反例。

### 3.3 Loon/QX 的嵌套、恢复切回和空组：仍是验收阻断条件

现有 Loon 附加同地区节点的做法能降低“只因嵌套被忽略而变空组”的风险，但该地区原本就没有节点时仍然为空，不能据此宣称全部空组安全。QX `available` 的官方说明强调触发后检测，不能仅用成员顺序推断恢复回切时限。两端都必须在目标版本真机验证。

建议将“已实现·未实测”细分为“结构已生成 / 语义待证”；README 对所有客户端统一承诺手动优先、恢复切回、更新保存选择，强于能力矩阵里的未知状态，应同步收窄。[Loon 官方示例](https://github.com/Loon0x00/LoonExampleConfig/blob/master/example.conf)、[QX 官方示例](https://github.com/crossutility/Quantumult-X/blob/master/sample.conf)

### 3.4 健康检查的时间承诺需要按客户端拆开

mihomo 的 provider 健康检查在 `emit_mihomo.py:215` 固定为 600 秒，而项目统一参数是 300 秒。源码显示相同 URL 的组检查注册不会覆盖 provider 检查间隔；引入 provider 节点的自动组不能只读组上的 300 就断定每个节点均每 300 秒重测。嵌套手动优先组有自己的检查，不能据此反向断言所有手动优先切换都要 600 秒。

同时，失败触发还受错误类型、时间窗口、lazy 和并发影响；“连续三次一定触发”“最迟 300 秒”不宜当作未经实测的保证。建议把统一参数当作期望，各后端额外报告实际生效参数和测量结果。[mihomo 健康检查源码](https://github.com/MetaCubeX/mihomo/blob/v1.19.31/adapter/provider/healthcheck.go)

## 4. 我建议补充的架构能力

这些是改进建议，不是认定当前已经造成故障。

1. **保留统一模型，增加“客户端能力合同”。** 每项能力声明精确支持、近似实现、不支持、待验证；生成时导出降级清单，尤其区分 Loon fallback、QX available 和 sing-box urltest。UI/README 与合同同源生成，避免承诺不一致。
2. **把规则匹配与 DNS 决策放进同一模型。** 每条内网覆盖可指定 route target、解析器和真实 IP/fake-ip 策略；对代理业务与 geosite-cn 等 DNS 分类交叉覆盖做审计。路由到美国不等于 DNS 查询也在美国。
3. **广告分成保守与激进档位。** 正常使用、认证、支付、消息、后台管理与纯广告应分开；社区标签只能当来源证据，不能自动升级成“安全可拦截”的业务结论。允许显式、可追踪的例外覆盖。
4. **固定运行时规则版本，或明确提供滚动更新档位。** 当前证据固定快照，但远程规则仍跟随 master/release 和自动更新；因此相同 ZIP 可能随日期产生不同匹配。稳定档位应锁定内容/hash，候选更新审查 diff 后发布。此项在原文已标为部分实现，不重复算新缺陷。
5. **用稳定节点身份与验证记录代替只信节点名。** regex 保留为初筛，另记录节点 ID、实际出口地区、验证时间、用途。多地区标签如“香港中转-日本落地”可能同时匹配多个地区；检测多重命中并报告，不能默默进入两国组。
6. **增加最小运行集成测试。** 官方解析+隔离本地代理/DNS 服务，验证直连、拒绝、节点消失、全失败、选择持久化、TCP/UDP 和 DNS 解析目的地。只检查组成员数组不算故障切换测试；现有模拟器仍有价值，但不能充当客户端行为的唯一证据。
7. **完整发布目录与机器可读验收摘要。** 保留上一个成功版本，所有步骤非零状态向外传播；摘要包含规则/生成器/依赖/内核/运行时集合 hash 与未验证项。下游代理应读摘要推进，不靠最后一句“成功”。
8. **补 Windows 入口与跨工具 ZIP 检查。** README 当前是 Bash 的 export/python3 示例，需提供 PowerShell 安全输入示例；直接把秘密字面量写进 export 仍可能进命令历史。ZIP 中文名没有 UTF-8 标志，本轮 Python 默认按 CP437 读出乱码，显式 `metadata_encoding='utf-8'` 才正确；Windows 解压正常。以后打包应设置 UTF-8 标志并做 Windows/Python 各一次解压验证。

### 7.7 对框架的补充建议

1. 给域名增加明确用途与范围：`产品 API / 共享认证 / 内容存储 / 安装下载 / 遥测 / 企业可选 / 历史候选`。相同厂商不必同组，共享认证也不宜被某个产品先抢走。
2. 建立机器可审计的候选生命周期：发现来源 → 后缀覆盖检查 → 官方/请求证据 → 共享服务审核 → 四端生成验证 → 真机功能验收。证据不足时留在候选区，避免“为了完整先全加”。
3. 保存上游提交或 SHA-256、抓取日期与来源依赖关系；失效 URL 让审核显示未验证，不静默沿用旧文件。定期更新需要另行建立维护流程，本次没有启用定时任务。
4. 对“根域已精确匹配，但上游为后缀”“已有通用国外覆盖，但未进入专用组”“本地规则未匹配，后续 GeoIP 未知”分别记录。普通字符串差集无法表达这些区别。
5. 以后扩展通配或 IP+端口时，先定义四端能力，再决定统一源语法；不能把 `*.foo`、标签内 `foo*`、任意深度后缀混成同一种匹配。
6. 新规则的真机验收应覆盖实际功能：登录重定向、Git LFS、分享链接、镜像拉取、活动加载、模型下载、Voice UDP。支付规则保持稳定出口，不以本轮审核直接触发真实交易。

### 7.9 逐项网址验证复核与结论修订（2026-09-30）

**确认范围：原列为建议补充、按功能补充或开发扩展的 44 个条目，全部有新抓取的官方用途文本核对及逐项网络检查记录；但不能确认它们全部在当前配置下完成了真实业务验收。** 这 44 项包含 20 个 Actions 存储主机，不是 44 种独立功能。社区候选没有因为“能打开”就升级为正式补充建议。

本次对 151 个具体主机逐项尝试 DNS、带主机名及证书校验的 TLS、HTTPS HEAD 根路径；另外 5 个官方模式/租户模板逐项核对表达，没有拿星号或占位串伪装成真实主机测试。所有记录均保存时间、响应或错误。151 项中 TLS 校验通过 131 项，本次未通过 20 项；根路径得到 HTTP 状态的 130 项，未得到状态的 21 项。HTTP 200 共 56 项，余下包括 400、403、404、405、406、530、502、204、401；这些数字是探测结果，不是业务通过率。

检查层次分别为：来源和用途 → 当前公开响应 → 现有精确/后缀覆盖 → 归组风险 → 真实业务验收。前四项已针对重点表执行并记录证据等级，第五项没有进行。TLS 为直接连接探测，HTTP 请求可能遵循当前环境的代理设置；本次没有加载被审配置、切换系统代理或使用账号。因此不能把探测结果写成“已经用这份配置登录、支付、播放或拉取成功”。公共根地址也不覆盖 WebSocket、UDP、签名对象 URL、地区节点或动态子域。
