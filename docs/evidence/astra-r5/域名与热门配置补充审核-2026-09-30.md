# 域名与热门配置补充审核

## 7. 域名与热门社区配置补充审核（2026-09-30）

**补审结论：有值得补充的专属域名和功能依赖，但不能把社区清单与本地规则的差集当成“全部遗漏”。** 最明确的新增项是 Grok 内容/认证域、GitHub LFS 专属存储主机和 Spotify 分享短链。Docker、支付、Discord Activities、开发工具和企业功能另有条件性扩展。以下全部是审核建议，未修改统一源或部署配置。

本节在阅读 README、审核说明、服务源和 `shared_excluded` 后，与官方现行文档、服务分类规则、整合规则及实际懒人配置的远程引用交叉核对。证据等级如下：

- **事实：** 文件实际存在的规则、后缀/精确匹配关系、官方文档列出的用途、下载时得到的状态。
- **判断：** 是否值得增加专用分组规则、推荐归组及优先级。
- **未验证：** 当前真实账号、节点、地区、业务 DNS、UDP 路径下是否失败；社区条目是否仍被客户端实际请求。2026-09-30 已补做公开 DNS/TLS/HTTP 检查，结果与限制见 7.9。

### 7.4 已知限制与新功能条件项：不能包装成新发现的疏漏

1. **Copilot 报表备用地址**：`copilot-reports-*.b01.azurefd.net`、`usagereports*.blob.core.windows.net` 已在 `ai.yaml` 的 `shared_excluded` 说明。它们是现有模型难以安全表达的标签内通配，不是作者漏看文档。可基于实际请求补精确主机，或以后扩展四端匹配能力；不要加整个 `azurefd.net`/`blob.core.windows.net`。
2. **Copilot 语音模型**：现行官方清单增加 Foundry Local 相关目录/下载要求。`ai.azure.com`、`api.catalog.azureml.ms` 没有本地覆盖；`*.api.azureml.ms` 可按后缀建模，`amlwlrt4*.blob.core.windows.net` 仍需要精确实例或额外匹配能力。这是模型下载服务，不能仅因出现在 Copilot 文档就认定 Copilot 独占。
3. **企业数据驻留**：`SUBDOMAIN.ghe.com` 是租户模板，需要真实企业域名。普通 github.com 用户无需为了“完整”添加它；也不能把占位串写入配置。

依据：[Copilot 官方清单](https://docs.github.com/en/copilot/reference/copilot-allowlist-reference)、[OpenAI 网络说明](https://help.openai.com/en/articles/9247338-network-recommendations-for-chatgpt-errors-on-web-and-apps)、[ChatGPT Voice IP JSON](https://openai.com/chatgpt-voice.json)。

### 7.6 比较后明确不应该“越多越好”的部分

- **共享云根域不能凑数。** 不把 `amazonaws.com`、`cloudfront.net`、`cloudflarestorage.com`、`azurefd.net`、`blob.core.windows.net`、`b-cdn.net`、`github.io` 整体分给一个产品。专属桶/主机可以单独审核。
- **`live-video.net` 不是 Twitch 独占。** DLC/BM7 的 Twitch 清单收了它，但 AWS 官方将其作为通用 IVS 流媒体基础设施；直接整体归 Twitch 会改变其他应用的出口。[AWS IVS 网络要求](https://docs.aws.amazon.com/ivs/latest/LowLatencyUserGuide/low-latency-network-requirements.html)
- **社区 AI 组不等于本项目 OpenAI 组。** 部分集合包含 `api.github.com`、`auth0.com`、`intercom.io`、`stripe.com`、遥测平台或所有 Claude/Poe；直接合并会破坏原有业务隔离。ACL4SSR/Sukka 的关键词类匹配也不能直接搬入当前禁止关键词的模型。
- **`chatgpt.site`、`crixet.com` 不作为 ChatGPT 聊天必需项。** 逐项当前访问已确认分别跳往 ChatGPT Sites 官方文档、OpenAI Prism；撤回笼统的归属证据不足判断。前者是用户托管内容功能范围，后者为旧入口/跳转候选；限制与证据见 7.9。
- **停止重复报已覆盖项。** Hugging Face 当前 8 个下载主机，包括 US/EU Xet 与多层 CDN 域，全部被现有 `hf.co` 后缀覆盖；`ghcr.io`、GitHub Releases、npm、Gradle 插件和 Docker 的 `production.cloudfront.docker.com` 也已有父域覆盖。[Hugging Face 下载文档](https://huggingface.co/docs/hub/models-downloading)
- **Apple AI 基线不因单个社区差异改动。** 本轮 Apple 官方 PCC/Siri/Search 所列六项已有规则。墨鱼列表额外出现 `apple-relay.akamaized.net`，官方当前表未列，保留为候选。`bahamut.akamaized.net` 和 YouTube 两个 API 精确主机也已覆盖；上游后缀更宽不是该主机遗漏。[Apple 企业网络说明](https://support.apple.com/en-us/101555)
- **Telegram IP 没发现官方清单遗漏。** 本次官方 CIDR 文本共 14 项，逐项与本地 Telegram 网络比较无缺项。这不等于 Telegram 所有功能已经真机验证。[Telegram 官方网络清单](https://core.telegram.org/resources/cidr.txt)

另外，官方 allowlist 与广告拦截并不天然一致。本次固定文本中，两个 OpenAI Sentry 租户会命中 Meta 广告集合和 QX AdvertisingLite，Loon 对应文本没有相同主机/父域命中。它们是已注明的遥测依赖，不能仅凭官方列出就自动放行，也不能声称四端当前远程广告结果完全一致；应由功能排错需求决定精确例外。

### 7.7 对框架的补充建议

1. 给域名增加明确用途与范围：`产品 API / 共享认证 / 内容存储 / 安装下载 / 遥测 / 企业可选 / 历史候选`。相同厂商不必同组，共享认证也不宜被某个产品先抢走。
2. 建立机器可审计的候选生命周期：发现来源 → 后缀覆盖检查 → 官方/请求证据 → 共享服务审核 → 四端生成验证 → 真机功能验收。证据不足时留在候选区，避免“为了完整先全加”。
3. 保存上游提交或 SHA-256、抓取日期与来源依赖关系；失效 URL 让审核显示未验证，不静默沿用旧文件。定期更新需要另行建立维护流程，本次没有启用定时任务。
4. 对“根域已精确匹配，但上游为后缀”“已有通用国外覆盖，但未进入专用组”“本地规则未匹配，后续 GeoIP 未知”分别记录。普通字符串差集无法表达这些区别。
5. 以后扩展通配或 IP+端口时，先定义四端能力，再决定统一源语法；不能把 `*.foo`、标签内 `foo*`、任意深度后缀混成同一种匹配。
6. 新规则的真机验收应覆盖实际功能：登录重定向、Git LFS、分享链接、镜像拉取、活动加载、模型下载、Voice UDP。支付规则保持稳定出口，不以本轮审核直接触发真实交易。

### 7.8 交付与验证边界

重点 151 个可作为主机名的条目，在现有四端生成文件的隔离模拟中逐项检查：远程集合设为空、DNS 未知时，结果与独立本地匹配计算 **没有矛盾（604 个域名×客户端组合）**。模拟器来自项目测试代码，所以这只是一致性复核，不能替代官方内核和真机。五个通配/租户模板不按真实主机测试。

另对重点域名核对 Meta 三份基线、BM7 两份广告列表、Loyalsoldier 三份通用列表。它们是本次取得的源快照，**不是用户设备里正在使用的缓存数据**；未把这些源文本当作 sing-box SagerNet 二进制数据的逐字节等价证明，也未推断真实 DNS/IP 最终路由。

本轮未逐个确认 52,210 个域名的归属、存续和真实业务请求；对这些输入完成的是自动静态对照。156 项重点表里也明确保留未确认项。全网服务没有封闭全集，不能据此承诺“没有任何遗漏”。可以确认的是：上述明确缺口及取舍已进入报告，全部候选有保留记录，原工程 **67 个文件再次与 ZIP 比较全部未变**。

### 7.9 逐项网址验证复核与结论修订（2026-09-30）

**确认范围：原列为建议补充、按功能补充或开发扩展的 44 个条目，全部有新抓取的官方用途文本核对及逐项网络检查记录；但不能确认它们全部在当前配置下完成了真实业务验收。** 这 44 项包含 20 个 Actions 存储主机，不是 44 种独立功能。社区候选没有因为“能打开”就升级为正式补充建议。

本次对 151 个具体主机逐项尝试 DNS、带主机名及证书校验的 TLS、HTTPS HEAD 根路径；另外 5 个官方模式/租户模板逐项核对表达，没有拿星号或占位串伪装成真实主机测试。所有记录均保存时间、响应或错误。151 项中 TLS 校验通过 131 项，本次未通过 20 项；根路径得到 HTTP 状态的 130 项，未得到状态的 21 项。HTTP 200 共 56 项，余下包括 400、403、404、405、406、530、502、204、401；这些数字是探测结果，不是业务通过率。

检查层次分别为：来源和用途 → 当前公开响应 → 现有精确/后缀覆盖 → 归组风险 → 真实业务验收。前四项已针对重点表执行并记录证据等级，第五项没有进行。TLS 为直接连接探测，HTTP 请求可能遵循当前环境的代理设置；本次没有加载被审配置、切换系统代理或使用账号。因此不能把探测结果写成“已经用这份配置登录、支付、播放或拉取成功”。公共根地址也不覆盖 WebSocket、UDP、签名对象 URL、地区节点或动态子域。
