二、确认的问题及依据

R13-F01：WireGuard 出口会触发目标域名解析，影响不只限于 TXT/SRV
类别：安全或泄漏、文档不符。严重程度：中等，触发条件明确。

位置：
- generator/emit_mihomo.py 第 238–240 行：nameserver-policy 仅有局域网例外和 geosite:cn,private → 国内 DNS。
- docs/03-DNS决策表.md 第 260 行：“只影响地址以外的查询类型”“连接本身不解析”。
- docs/06-已知限制与待决事项.md 第 22 行，待决事项 16：同样的影响范围说明。
- tests/cases.yaml 第 422 行，product_cn 的 why。
- tools/check_real_routes.py 第 598–602、659–662 行：代理策略组在核对时换成 REJECT。

为什么不成立：
DNS 监听端口返回 fake-ip，不等于所有代理协议建立连接时都不用解析目标。WireGuard 是 IP 隧道出口。mihomo v1.19.31 的 WireGuard 在目标还没有真实 IP、又没有配置专用远程解析器时，会使用 resolver.DefaultResolver 解析目标域名。qwen.ai 的连接虽然已由产品规则分到“国外默认”，DNS 策略仍会命中 geosite:cn，使用国内 DNS。

官方依据：
- https://github.com/MetaCubeX/mihomo/blob/v1.19.31/adapter/outbound/wireguard.go
  第 87–88 行：remote-dns-resolve、dns 选项。
  第 508–520 行：只有 remote-dns-resolve 为 true 且 dns 非空，才构造专用解析器。
  第 794–810 行：DialContext 对未解析目标使用默认解析器；UDP 对应分支在第 839 行附近。
- https://wiki.metacubex.one/config/proxies/wg/
  官方说明 remote-dns-resolve 默认 false，dns 与它配套使用。

本轮复现：
- 官方 mihomo v1.19.31，使用本分支生成的 mihomo-core.yaml，保留原有路由及 DNS 策略结构。
- 按工程现有探针方法，把 system／国内／境外 DNS 分别替换成三个本机 UDP 替身；A 只答 127.0.0.1，其他类型回空。
- 关闭 TUN、系统代理和外部控制端口，只在本机监听代理端口。
- 将“国外默认”固定到一个测试出口；分别运行 SOCKS5 对照和 WireGuard。测试服务器都是 127.0.0.1 的空端口，WireGuard 使用临时随机测试密钥，不读取真实订阅。
- 经代理端口请求 CONNECT qwen.ai:443，保持连接供内核进入拨号阶段。

只统计 qwen.ai 的结果：
SOCKS5：system 无查询；国内 DNS 无查询；境外 DNS 无查询。
WireGuard（未设 remote-dns-resolve/dns）：system 无查询；国内 DNS 收到 A 和 AAAA；境外 DNS 无查询。

WireGuard 内核日志顺序：
[DNS] resolve qwen.ai A from udp://127.0.0.1:<国内替身端口>
[DNS] resolve qwen.ai AAAA from udp://127.0.0.1:<国内替身端口>
[DNS] qwen.ai --> [127.0.0.1] A ...
之后才出现 WireGuard 握手及本机端口拒绝。

这证明的是目标查询进入了国内 DNS 路径；实验未向真实国内 DNS 发送该查询，也没有声称完成了 WireGuard 联网。未查看用户的真实节点，因此不表示用户当前一定受影响。

现有测试为什么看不到：
代理组换成 REJECT 后，目标匹配规则便结束了；新增的静态断言约束默认 DNS 和 resolve 动作，同样没有运行 WireGuard 的出站解析。因此这类测试中 qwen.ai 的 none 只能说明该测试路径没有查询，不能推广到所有代理出口。

建议：
1. 先更正文档、待决事项 16 和 cases.yaml 的影响说明，明确区分“设备向 DNS 端口查询”与“代理出站为连接解析目标”。
2. 增加一条实际 WireGuard 出站的本机探针，用 SOCKS5 作对照；保留 DNS 去向观测，即使握手失败也能验证此路径。
3. 如果选择解决此问题，再按待决事项 16 的第二方案，从统一源／生成器为代理产品域名生成优先于 geosite:cn 的境外 DNS 策略，并核对重叠、长度、实际解析及故障行为。另一种节点级方案是正确配置 WireGuard 的远程 DNS，须同时验证其可达性和传输路径。
4. 不能只打开 respect-rules 或更换图标来解决；前者控制 DNS 连接怎么出站，不会自动把目标域名重新归到境外 DNS。

对我上一轮审核的更正：此前对 142 个域名查询结果的观察，只能证明 DNS 前端行为。我认可“连接本身不解析”的概括过宽，应以本次条件说明为准。

R13-F04：DNS 记录名的混合压缩形式仍解析失败
类别：核对工具错误／改进建议。严重程度：低。

位置：tools/check_real_routes.py 第 207–214 行；tests/test_real_data.py 的 ProbeReplyParsing 未覆盖此种记录名。

原因：
当前循环只在记录名第一个字节检查压缩指针；进入普通标签分支后，把后续每个字节都当成标签长度。因此“cdn + 指向 example.com 的指针”中的 0xc0 会被当成长度 192，发生越界，返回 (-1, [], 0)。reply_kind 继而显示 rcode--1。

这不是畸形报文。RFC 1035 第 4.1.4 节允许标签序列以压缩指针结束：
https://www.rfc-editor.org/rfc/rfc1035.html#section-4.1.4

本轮本机 UDP 复现：
问题：www.example.com，类型 A。
正常应答：RCODE=0，ANCOUNT=2。
第 1 条：www.example.com CNAME cdn.example.com。
第 2 条：cdn.example.com A 192.0.2.7。
第 2 条的 owner 编码为 03 63 64 6e c0 10；0x10 指向问题区的 example.com。

期望 dns_exchange：(0, ['192.0.2.7'], 2)
实际 dns_exchange：(-1, [], 0)
实际 reply_kind：rcode--1

建议：
提取跳过 DNS 名字的函数，在每个标签边界判断：零表示结束；高两位等于 11 时占两个字节并结束当前名字；否则按普通标签推进。此工具只需跳过记录名，不必为了定位后面的 TYPE/CLASS 去展开指针内容。补一条 CNAME+A 的混合压缩样例即可。

本项没有证据表明当前固定探针结果因此错误：现有替身答复和 fake-ip 应答大多用完整指针，刚好绕过了问题。它也不会改变四端生成配置。r13 对 AAAA／非地址记录误判为空的修复仍然成立，但不能表述为解析器已覆盖所有合法 DNS 答复。

6. 没有重复报的已知限制
远程规则仍引用 main、严格版尚未随 main 发布、用户待决的 15–20 项、上游不锁版本、GUI／真机验收边界，说明已经明确，本轮不把它们重新算作新增错误。

五、验证边界与处理顺序

本轮没有运行完整 100 类变异检查，也没有重新运行全部逐条扫描；没有把历史日志计为本轮实测。sing-box 的本轮结论限于官方 check 和静态／单元测试，未取得新的完整运行时 DNS 证据。Loon、QX、macOS 和真实机场出口未做真机验证。

建议先处理 R13-F01 的风险说明和实际出站测试，再修正 system 的源码解读；压缩名解析与覆盖统计均可分别作为小范围独立提交。是否改变待决事项 16 的生产 DNS 策略，仍应按用户已确定的取舍决定。修复时从 source／generator 改动并重新生成，历史 evidence 日志和原始需求不应改写。
