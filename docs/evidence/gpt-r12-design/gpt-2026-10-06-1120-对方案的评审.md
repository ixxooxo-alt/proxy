依据：[Loon 订阅规则文档](https://nsloon.app/docs/Rule/sub_rule/)、[Loon 开发者应用说明](https://apps.apple.com/us/app/loon/id1373567447)、[Quantumult X README](https://github.com/crossutility/Quantumult-X)。:chatgpt-content-reference{index="25"}

**这里我不能给你编造“设置→某按钮→某页面”的逐级路径。**以下是依据已确认功能可执行的检查顺序，页面入口位置仍须在当前版本上核实。

### Loon 的操作与判读

1. **先清理测试状态。**停止并重新开启 Loon，使用一个此前未访问过、能够正常解析的新测试域名。官方说明其运行期 DNS 缓存会在关闭后清除；但仍建议每次换新的随机子域名，减少其他缓存干扰。:chatgpt-content-reference{index="26"}
2. **从 Safari 或实际业务 App 发起访问，不要用 DNS 查询工具代替。**在请求记录中找到该域名，打开详情，记录命中规则、策略及最终出口。
3. **在 DNS 结果记录中寻找同一个完整域名。**若页面显示上游服务器，记录它；若只显示解析 IP 或耗时，**这些信息不足以回答“问的是哪台 DNS”**，需要下述外部观测。

### Quantumult X 的操作与判读

1. 同样使用每次不同的新域名，并确认所测试的配置、远程资源已经生效。技术人员也可用[官方 DNS API 示例](https://github.com/crossutility/Quantumult-X/blob/master/sample-dns-api.js)中的 `dns_clear_cache` 清理客户端缓存。:chatgpt-content-reference{index="27"}
2. 在**请求历史**中找到连接，查看完整策略链，确认确实经“国外默认”发出。
3. 在**DNS 结果记录**中找同名记录，查看首个响应服务器、时间和 TTL。若显示国内上游，同时该连接走代理，就已发现不符合目标的情况。:chatgpt-content-reference{index="28"}

### 什么结果才算证明？

**看见国内 DNS 查询，是明确的失败证据；没看见记录，不是充分的通过证据。**

没有记录可能是缓存、占位 IP、本次日志未覆盖该路径等原因；而只记录首个响应服务器，无法排除另一个上游也收到过并发查询。Loon 和 QX 的官方资料都存在并发查询描述。:chatgpt-content-reference{index="29"}

要确认“有没有查询、问了谁”，应由测试者配合：

- **受控测试 DNS 的服务端日志**：能直接确认收到的域名和请求。
- **手机真实流量的外部抓包**：可以确认连了哪些 DNS 地址；加密 DNS 的域名内容通常还需要受控解析器日志才能对应。

不要只使用权威 DNS 日志来推断手机直接问了谁：中间可能还有递归解析器。

### 最少应覆盖的验收用例

| 用例 | 要验证的结果 |
|---|---|
| 已有产品代理域名、未列入任何集合的新域名 | 均不向国内 DNS 发出该目标域名查询 |
| 国内域名、纯国内 IP、局域网 IP、Telegram IP | 仍按预期直连或进入指定策略 |
| 同时命中“国内 DNS 集合”和“强制代理规则”的域名 | 不因集合冲突先发生国内解析 |
| DoH 超时、证书失败、返回错误 | 不出现未经允许的回落 |
| 广告与国内集合重叠、远程资源缺失 | 不被新兜底抢走，也不静默失去保护 |
| 真实 IP 例外、IPv6、Wi-Fi／蜂窝切换 | 路径与普通测试一致，或明确记录例外 |

这是我建议的验收标准，不是声称这些用例已经跑过。

## 9．对方遗漏的风险：最重要的是 DNS 规则与连接规则不一致

### 风险一：mihomo、sing-box 也可能存在“先国内解析，后代理”的组合

**结论：不能直接给这两端盖章“不用改”。可以暂不改，但必须新增集合冲突测试。**

根据你提供的结构，可以构造这样的情况：

> 某域名进入国内 DNS 集合 → 国内 DNS 已收到查询 → 解析结果不属于国内 IP，或另一条产品规则要求代理 → 最终走“国外默认”。

**sing-box 尤其需要检查**：你把国内域名 DNS 规则放在 fakeip 规则之前，意味着属于该集合的查询有机会先真实解析；后面路由再选择代理，也无法撤回已经发出的 DNS 查询。

mihomo 的假 IP 会减少普通 A／AAAA 请求中的真实查询，但不能据此排除真实 IP 例外、其他记录类型，以及需要真实解析时的策略交叉。DNS 规则和路由规则是分别配置的，这正是必须检查一致性的原因。:chatgpt-content-reference{index="30"}

**把握程度：根据你描述和官方机制得出的推断，不代表我已经发现实际命中的域名。**

### 风险二：规则名称不能代表最终动作

“国内直连”若是可切换策略组，而不是固定 DIRECT，或者用户之后切换全局模式，就可能出现**已经按直连政策国内解析，连接却改走代理**的情况。

建议把“允许国内 DNS 的域名集合”与**实际保证直连的动作**绑定，并把模式切换列为验收项。这是状态变化带来的工程风险，不是某款软件特有的问题。

**把握程度：推断。**

### 风险三：规则源统一，不代表运行时快照统一

生成器使用同一 YAML，但四个客户端若独立更新远程清单，仍可能运行不同时间的数据。建议在交付中固定规则快照或记录版本、校验值，避免某端已增加国内 DNS 分类，另一端还没有对应路由修正。

**把握程度：工程建议。**

### 风险四：只检查几个国内 DNS 地址，范围太窄

不要把检测逻辑写成只检查你列出的三四个 IP。一个具体例子是：核对的 Clash Verge Rev v2.5.7 macOS TUN 代码中，存在设置系统 DNS 为 `114.114.114.114` 的调用。**这不等于它必然泄露**，但说明系统侧和客户端侧可能还有其他解析器来源，必须检查最终环境。:chatgpt-content-reference{index="31"}

此外，应用自带解析、DNS 例外、不同记录类型，也不能只靠一次浏览器 A 记录测试排除。:chatgpt-content-reference{index="32"}

**把握程度：**上述源码行为**已查证**；你的设备是否涉及这些路径**不知道**。

### 风险五：“交给节点解析”不自动证明节点使用的不是国内 DNS

客户端不再本地查询，只能证明消除了相应客户端查询路径。**节点最后使用哪台解析器，还取决于节点端。**如果你的目标包含“任何环节都不能交给国内 DNS”，节点端也必须纳入验收，不能把“远程解析”直接当成这个更强目标的证明。

节点地址本身的启动解析，也应与业务目标域名分开记录，避免既误报，又漏掉真正的目标域名查询。

**把握程度：架构推断；节点端实际设置未知。**

**最终结论：改成“Loon 优先验证 GEOIP＋no-resolve、Quantumult X 用域名兜底保留纯 IP 分流、四端统一检查 DNS 与路由集合冲突、两份配置交付并完成 iPhone 验收”后再做；不要原样实施，也不要提前承诺“完全不泄露且所有国内网站零影响”。**
