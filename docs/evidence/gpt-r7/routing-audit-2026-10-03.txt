二、需要优先改善的逻辑

F01 / P1：Qwen 的“国外默认”意图没有进入实际路由

位置：source/services/ai.yaml:220；dist/mihomo/mihomo-core.yaml:1652；sing-box 的 geosite-cn 路由及 DNS 规则。

源文件在 shared_excluded 中说明 qwen.ai / chat.qwen.ai 应落入国外默认。但 shared_excluded 只是排除或证据说明，没有生成优先于国内分类的强制路由。当前上游国内集合包含 qwen.ai，国内集合又在最终国外出口之前。

本轮验证：保留原始规则，使用官方 mihomo v1.19.31 和下载的 GeoSite 数据，在隔离测试中得到：
   qwen.ai:443       → GeoSite(cn) → 国内直连
   chat.qwen.ai:443  → GeoSite(cn) → 国内直连
   openai.com:443    → DomainSuffix(openai.com) → OpenAI（对照）

隔离测试把所有业务组出口替换成 REJECT，仅验证匹配结果，不外连。原始配置的“国内直连”默认是 DIRECT；日志中的 REJECT 是测试替身，并非原始配置把 Qwen 拦截。

sing-box 下载的实际 geosite-cn.srs 反编译后同样包含 qwen.ai，其原始规则顺序也会让该域名先命中国内组。这一项是规则与实际集合的核对，没有冒充 sing-box 的完整网络实测。

DNS 也使用国内集合优先匹配，因此只补连接路由，未必同时改变解析路径。

建议：将“必须走某策略”的业务例外表达为显式规则，放在 GeoSite 国内分类之前；相应 DNS 例外一起审查。将“仅不收录”与“强制国外路由”区分为两种语义。新增最终路由断言，输入实际下载的 GeoSite / SRS，而不只检查本地源里有没有该域名。

数据库会更新，此结论对应本轮记录哈希的快照，不代表上游永远如此。

F02 / P1：信息节点过滤过宽，真节点式描述会让节点消失

位置：source/regions.yaml:29；generator/regions.py:578。

补充反例（人为构造，用于边界验证，不是用户的真实订阅）：
   日本 01 全网站解锁                 → 不进入任何组，命中“网站”
   Japan 01 | Unlimited Traffic      → 不进入任何组，命中 Traffic
   美国 01 ChatGPT官网可用            → 不进入任何组，命中“官网”

这是所有地区组连同“其他地区”一起排除，不只是分错到其他国家。项目文档已承认信息词表可能误伤，本轮给出了更接近日常宣传描述的反例。125 项测试通过不消除这类语义风险。

建议：优先匹配结构化提示，例如“剩余流量 + 数值单位”“套餐到期 + 日期”“重置剩余 + 天数”，减少任意位置单词命中即删除。无法确定的信息行可先报告或进入待确认范围；本地精确指定继续作为覆盖入口。测试同时加入真节点描述和真实提示格式，明确误删与漏收的取舍。

F03 / P1：解锁说明的冒号会改变国家归属

位置：source/regions.yaml:39；generator/regions.py:391、524。

补充反例：
   日本01 | 解锁 美国    → 日本
   日本01 | 解锁: 美国   → 日本、美国

原因：用于排除“解锁 / 经由”等描述的前置判定只覆盖有限的空白写法，没有覆盖冒号一类常见分隔符。正则和独立分类器给出相同结果，说明不是某一个输出端偶发的正则错误，而是两套实现共享了同一语义缺口。

建议：先定义节点名中的落地、中转、解锁和宣传字段，再做匹配；短期至少统一处理半角 / 全角冒号、多空格和括号，并同时覆盖生成正则与分类器。不要仅继续追加城市词表。

F04 / P1（设计取舍）：歧义节点同时进入两个国家自动组

位置：source/regions.yaml:13；generator/regions.py 的国旗、地区合并分支。

日本-美国 01、🇯🇵 Tokyo 01 🇺🇸 等名称会同时进入日本和美国组。这是当前已记录的设计，不是遗漏的实现错误。

影响：名称无法证明实际落地，一个实际在美国的节点可能被日本自动组选中；“组内切换”不等于“实际出口不跨国”。没有真实出口实测时，不应把按名称筛选描述为地理保证。

建议：若“同国切换”是硬要求，歧义节点应先只进待确认 / 手动范围，完成本地指定或实测后再进入自动、故障转移和负载均衡组。待确认范围不必增加首页业务策略组，可隐藏在维护流程中。保留检查工具的可解释报告。

F05 / P2：含糊城市词的优先级高于明确国家词

位置：source/regions.yaml:136；generator/regions.py 的 other_countries 优先级。

补充反例：
   美国 奥克兰 01        → 其他地区
   US Oakland 01        → 美国
   香港 01 纽约时报解锁  → 美国

第一例的“奥克兰”被作为其他国家依据，覆盖了明确的“美国”；最后一例把媒体名称中的“纽约”当作落地，随后触发香港让位。它们说明“命中文字子串”与“识别地点字段”不同。

建议：区分国旗、明确国家、城市、服务描述等证据强度；存在冲突时报告歧义。不要简单把“奥克兰”全部改归美国，它也可能指其他地点。香港让位可以保留为已知机场命名规则，但不宜对任意宣传句中的城市词无条件生效。

F06 / P2：DNS 说明中的结果保证过强

位置：docs/03-DNS决策表.md:20；docs/06-已知限制与待决事项.md:30。

文档说 Loon / QX 未命中域名规则的境外域名会先交国内 DNS，“结果仍会走国外默认”。后一半缺少条件：如果解析结果命中国内 IP，GEOIP,CN 就会直连。因此不能保证所有未分类境外域名最终都走国外默认。污染、地理 CDN 或共享基础设施都可能影响这个分支；本轮没有观测用户网络上的实际污染。

当前国内站点、节点服务器域名使用国内 DNS 有明确设计理由，不能一概称为异常泄漏；但也不应宣传“四端零国内 DNS 可见性”。Loon 官方文档还说明加密 DNS 失败默认可以回落到普通 DNS，这个开关在 App 中控制。QX 的官方示例则说明启用 DoH / DoQ 时会忽略通用非加密服务器，不能把 Loon 的回落行为照搬给 QX。

建议：把说明改成条件式结论。若目标是让未知境外域名也尽量走代理解析，采用经审查的精确域名 / 后缀集合与分域 DNS；对含宽泛关键词的上游集合可以做过滤输出，而非直接整包引入。实施前验证节点域名解析和规则下载不会形成启动依赖循环，并评估国内 CDN 延迟的变化。

三、框架与语法评审

建议保留的部分

• source 统一定义业务、地区、DNS、证据，生成器输出不同客户端；避免四份配置独立维护。
• 规则计划与客户端语法转换分离；专属服务规则先于大厂和最终分类。
• 业务组 → 地区 / 专用入口 → 模式 → 节点的分层。日常切换地区和调整节点模式各有入口，结构合理。
• 缺失引用、循环、节点重名等在生成时检查；不能只依赖 sing-box check。
• mihomo 地区空组指定 REJECT，sing-box 空组用阻断占位；保持失效时不自动改成 DIRECT 的原则。
• 私密补充、节点转换报告、统一生成后的产物一致性检查。

需要收窄的兼容性承诺

1. mihomo：本轮证明的是 v1.19.31，建议把最低已验证核心明确写出来。不要只写宽泛的 v1.19.x，也不要在没有版本历史证据时断言某字段恰好从 v1.19.31 才引入。

2. sing-box：1.14 产物与 1.12 兼容产物分别检查的安排合理。当前阻断占位在已测试核心中可用，不作为现有语法错误。后续升级应对出站格式、DNS 和规则集字段重跑检查。

3. Loon：现行官方文档支持策略组嵌套，但旧官方示例对自动类嵌套的描述不同。现有 emitter 加入同地区节点作为兼容退路有考虑；仍需看目标 App 中实际展开的成员和失效后的行为，不能仅靠配置文本保证恢复切回时限。

4. QX：官方 sample.conf 对 server-tag-regex 的适用策略，注释与示例存在不一致。当前使用的 url-latency-benchmark、dest-hash 不应直接定性为错误，也不能未经设备验证就保证能按地区取节点。

5. 超长正则：QX 每个模式重复正则，配置约 326 KB；Loon 约 126 KB；mihomo core 约 139 KB。需要验证实际 App 的长行接受能力、导入耗时和成员正确性。若不兼容，再提供明确标注能力差异的短规则版本。没有必要在尚未发现实际问题时全面改写框架。

6. 各端能力不同：sing-box 没有与另外几端等价的故障转移 / 负载均衡策略组；广告拦截是路由 reject 动作，不能通过同名选择组一键关闭。现有能力矩阵应继续保留这些区别，避免“同名即等价”的 UI 暗示。

四、业务维护建议

1. 广告规则按用途再分层
   source/adblock.yaml 中 marketingplatform.google.com、advertising.apple.com、analytics.google.com 会涉及广告主或分析后台；umeng.com / umengcloud.com 还可能涉及推送和登录。源文件已经标注部分风险。
   建议将广告投放、统计遥测、业务管理后台在源模型中分别标识，并提供精确例外。上游标记为广告，不等于阻断后对所有业务都无影响。无需为此增加多个首页策略组。

2. PayPal 固定名称与稳定出口要分开
   当前 pinned_node_name 为空，入口实际上是美国节点中的手动选择；节点移除后可能选择另一节点。即使绑定名称，也不代表供应商永不更换出口 IP。
   建议显示“未绑定 / 已绑定”的状态，并在绑定后明确节点消失时的行为；稳定出口需实际测量记录，而非只看名称。

3. Netflix 的解锁状态保持显式
   verified_node_regex、verified_region、verified_at 目前为空，退化为地区选择是明确的现有设计。
   建议有验证记录后再启用“已验证”标识，并记录同国约束和复测时间；普通健康检查的 204 成功不能代替 Netflix 解锁测试。

4. Apple AI 的宽域名覆盖是业务取舍
   source/services/bigtech.yaml 包括 ls.apple.com、apps.mzstatic.com 等共享服务范围，可能带动地图 / 定位、商店资源随 AI 组出口变化。源文件已说明这些副作用。
   若坚持现有 Apple AI 需求，可保留；若遇到功能或延迟问题，优先缩小有证据支持的主机范围或添加功能例外，不宜扩到全部 Apple 域名。

5. 保留远程规则跟随上游的既有决定
   不建议以本次审核为由强制改成版本锁定。可以记录每次下载的哈希、变化摘要和上一份可用缓存，再对 Qwen 这样的关键业务做路由断言；既保留自动更新，也能发现语义漂移。

6. 测试重点应转向独立的业务结果
   已有单测和跨引擎一致性基础不错。下一批有价值的测试应是“给定域名与数据库快照，最终路由 / DNS 应是什么”“有宣传字样的节点不能无故消失”“歧义节点不能进入受限制的自动组”，而不是仅重复验证生成器输出和自身分类器一致。
