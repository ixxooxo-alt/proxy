## 推断（有依据，但没有运行验证）

- mihomo 的“手动优先”：源码显示 fallback 组选第一个健康成员，成员是组时对其当前选择做检查，连续连接失败会触发检查；因此手选节点失效后会切到同地区自动组，恢复后切回。
- mihomo 筛选为空时默认落到 COMPATIBLE（源码中是直连出站），因此设了 `empty-fallback: REJECT`。
- Loon 规则优先级（本地 > 插件 > 订阅；域名先于 IP）来自官方文档；Quantumult X 的优先级来自社区文档，其中“域名类先于 IP 类”“本地先于远程”两点有官方示例和官方仓库的用户报告可以印证（`docs/02`“严格版用到的写法”）。
- 各端字段语法见 `docs/02-语法依据与能力矩阵.md`。
- **mihomo 查 `nameserver-policy` 的方式**（r14 用到）：相邻的普通域名写法合成一棵域名树、越具体越优先、不看先后，`geosite:` 的条目按书写顺序——读 v1.19.31 源码得到（`dns/resolver.go` 的 `makePolicy`、`component/trie/domain.go`），核对工具照这个写，测试里的例子也是按源码人工写出的，没有用官方内核单独验证。这一版的配置不依赖它：更具体的写法恰好都写在更宽的前面，按“第一条命中”查结果也一样（一次性核对 `handoff/notes/r14_policy_order.out`，2,235 个主机）。官方内核核对过的是结果（上表“出站时的解析”、逐条扫描里的 432 个主机）。
- **严格版靠推断的四处**（`docs/02`“严格版用到的写法”表里标了推断的）：Loon 单独一行的 `GEOIP,CN,策略,no-resolve`；Loon 多条订阅规则之间按书写顺序；Quantumult X 远程资源之间按书写顺序；Quantumult X 远程资源里的域名规则先于本地的 IP 规则。模拟器是按这些推断写的。
- **Loon、Quantumult X 的节点筛选正则由 ICU 执行**：两者是苹果平台的原生应用，推断用的是系统自带的 `NSRegularExpression`（底层是 ICU）。官方没有说明；旁证是官方与社区示例里的写法 ICU 都支持。所以“在 ICU 上结果一致”只能推出“在这两个 App 里大概率一致”。
- **mihomo 用真实订阅时走的路径与检查时相同**：检查用的是本地文件订阅，真实使用是 http 订阅；两者取到节点后都由 `GroupBase.GetProxies` 用同一条 `filter` 筛（源码）。另外，组的测速地址和订阅上的相同时，mihomo 不会把组的 `filter` 再拼进健康检查（源码 `healthcheck.go` 的 `registerHealthCheckTask`：`url == hc.url` 时直接返回），本项目两处用的是同一个地址。

- **Loon 的第二个广告列表文件**（`AdvertisingLite_Domain.list`，每行一个域名）能否被 Loon 当作订阅规则解析：官方文档没有写这种格式，依据只有上游规则库的说明。
- **Loon / Quantumult X 的路由**：没有能在电脑上运行的官方内核，这两端（标准版和严格版）的“真实数据核对”用的是自制模拟器（规则优先级按官方 / 社区文档实现，严格版另有四处推断），不是 App 本身。
- **真实网络下的 DNS**：mihomo、sing-box 的 DNS 去向和“走代理的域名不交给国内 DNS”的四项核对，都是在本机用假 DNS 服务器做的（看查询被交给哪个服务器），入口是代理端口和临时的 DNS 端口，不是虚拟网卡；第四项“出站时的解析”用的出口是连本机空端口的 SOCKS5 / WireGuard 出口，不是真实节点，Shadowsocks、Trojan 只在一次性核对里试过（`handoff/notes/r13_review_probes.*`，r13 和这一版的配置各一遍），别的协议没有试；没有在真实网络里观测解析结果，系统在虚拟网卡之外自己发出的查询、浏览器自己的安全 DNS 不在核对范围里。“境外 DNS 不应答时不回落”只试了“只收不答”这一种失败方式；Loon / Quantumult X 上未分类域名解析到国内 IP 的实际比例没有观测。
- **mihomo 产品域名那一层（r14）在真机上的效果**：只在本机用官方内核和替身核对过（上表）。代价那一面也没有实测：这些组被你手动切成直连时，名字由境外 DNS 解析，可能连到离你远的服务器（`docs/03` 最后一节）；默认直连的组（Apple 等）被你切到代理以后，名字仍交给国内 DNS（待决事项第 17 项同一类）。Loon、Quantumult X 转发 UDP 时会不会在本机解析目标域名，官方文档没有写，不知道。
- **Qwen 国际版实际使用的主机**：只按上游列表收了 `qwen.ai`、`qwenlm.ai`，没有抓过它的实际连接。
- **手机上筛选节点的耗时**：只有按这台机器估算的数（300 个节点：Loon 约 36–38 毫秒，Quantumult X 约 63–66 毫秒，2026-10-05 几次运行的范围；手机会慢几倍）。
- **Clash Verge Rev、Clash Meta for Android 的界面层**读取带 YAML 锚点 / 别名的配置：内核已验证，客户端自己的处理没有验证。
- **真实订阅的节点名**：分组规则只用归纳的样本、审核方构造的反例和独立来源的国家 / 城市名检验过，没有用任何一家机场的真实节点名检验。r10 把“地名 + 中转”“国旗 + 中转”“只在解锁说明里提到地区”的节点从自动类的组里拿掉了：你的机场有多少节点是这种写法、自动组会少多少，要看真实的节点名才知道。反过来，规则不认识的中转说法（`经由`、`跳板`、`Entry` 等，`docs/06`）在真实订阅里有多少，也要看了才知道。
- **`tools/check_icu.py` 在 Windows、macOS 上**：只在 Linux 上跑过；另两个平台找不到或加载不了 ICU 时会报告“没有做检查”（那一项测试自动跳过）。
- **所有真机行为**：接管范围、DNS、IPv6、故障切换时长、选择保持、广告效果、解锁、实际出口，全部未测。
- **规则归属的实际效果**：社区来源已对照固定快照，但那只说明上游维护者也这样归类；21 条维护者知识、5 条“需求指定”、9 条“从另一版导入”的广告没有同值的外部佐证。见 `docs/06-已知限制与待决事项.md` 的“证据强度”。
