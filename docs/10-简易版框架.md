## 三、结构

```
服务组（OpenAI、YouTube 等，和完整版一样）
  └ 选一个：默认地区 / 国外默认 / 香港 / 日本 / 韩国 / 台湾 / 新加坡 / 美国 / 其他地区 / 直连

日本（六个明确地区都一样）
  ├ 日本·自动（默认）：在名字只指向日本的节点里自动测速，用能用的、最快的；挂了自动换，只在日本里换
  ├ 日本 01
  ├ 日本 02 …… 这个地区的全部节点（含名字说不清落地的）。点一个 = 固定用它，挂了不会自动换

其他地区：只能手选（里面国家混在一起，不做自动）
国外默认：日本 / 香港 / 韩国 / 台湾 / 新加坡 / 美国 / 其他地区 / 全部节点（默认日本）
PayPal·美国固定、广告拦截、国内直连：和完整版一样
```

### 3.1 各组

| 组 | 类型 | 成员 | 首次导入时选中 | 和完整版比 |
|---|---|---|---|---|
| 服务组（43 个；sing-box 是 42 个，它的“广告拦截”是规则动作，不是组） | 选择 | 照旧 | 照旧 | 不变 |
| 日本等六个地区 | 选择 | “日本·自动”，再接宽筛选取到的节点 | 日本·自动 | 完整版里这是“选模式”的入口 |
| 日本·自动等六个 | 自动测速 | 严筛选取到的节点 | — | 不变（完整版也有，名字也一样） |
| 其他地区 | 选择 | 其他节点 | 第一个 | 不变 |
| 国外默认 | 选择 | 七个地区，再接全部节点 | 日本 | 多了全部节点 |
| PayPal·美国固定 | 选择 | 美国节点（宽筛选） | 第一个 | 不变 |
| 去掉的 | — | 每个地区的手动优先、手动、故障转移、负载均衡（共 24 个） | — | — |

- **宽筛选、严筛选**：现在就有的两条按名字分地区的正则（`docs/02`“节点名称分地区”）。宽的收这个地区的全部节点，包括名字说不清落地的（人来选）；严的只收名字只指向这个地区的（让 App 自己挑时，不会挑到别的国家去）。
- **全部节点**：订阅里的全部节点，去掉机场插进来的提示行（“剩余流量”“套餐到期”等，`source/regions.yaml` 的 info 规则）和本项目的占位（“…·无可用节点”，Stash、sing-box 上有）。
- **地区一个节点都没有时的处理照旧**：mihomo 写 `empty-fallback: REJECT`，sing-box 放一个拒绝连接的占位出站，Stash 放一个连不上的占位节点，都是连接失败而不是直连；Loon、Quantumult X 上筛选为空时会怎样，没有依据（`docs/02`“节点筛选为空时”）。简易版的地区组里总有“X·自动”，组本身不会是空的。
- **没有新的组名**：“日本”“日本·自动”“国外默认”等都是完整版已有的名字，图标都已登记，不需要新图标（第八节核对）。

### 3.3 怎么用（写给使用者）

- 服务组里选地区，例如 OpenAI 选“日本”。
- 打开“日本”：选“日本·自动”，它自己挑同地区能用的节点；点某个节点，就固定用它。只有这一层，不用再点进子组。
- 建议：给 AI 用的那个地区固定一个节点（IP 不会自己变）；其他地区保持“自动”。
- 固定的节点挂了不会自动换：回到“日本”里点“日本·自动”，或者点别的节点。
- “国外默认”里尽量选地区，不选单个节点，原因见第六节。

## 四、各端怎么写、依据

### 4.1 sing-box（SFA）

- 写法：`日本` = selector，outbounds 为 `["日本·自动", 日本的各个节点…]`，default `日本·自动`；`国外默认` = selector，outbounds 为七个地区再接全部节点，default `日本`。节点本来就是本机转换后写进配置的，筛选在生成器里用 Python 做（和现在一样）。
- **事实（源码）**：sing-box 只有 selector、urltest 两种组（`constant/proxy.go:49-50`），没有故障转移；SFA 只能在 selector 里点选（`daemon/started_service.go:595` 只有 `*group.Selector` 算可选，`:757` 不是 selector 就拒绝）。所以“手动优先、挂了自动换”在 sing-box 上做不出来，方案 ③ 正好不需要它。
- **事实（本机实测，1.14.1 和 1.12.0）**：上面这种一层写法两个版本都能用；在“日本”“国外默认”里直接选节点立即生效；选中的节点停掉以后不会自动换，请求一直失败（`handoff/notes/simple_singbox/` 的 `114-simple_onelayer`、`112-simple_onelayer`）。
- 1.14 版和 1.12 兼容版的策略组逐项相同，差别只在规则集怎么下载，所以简易版也是这两份（sing-box 没有严格版）。
- 和完整版的实际差别：完整版的 sing-box 本来就没有手动优先，地区是“自动 / 手动”二选一；手选节点要先在“日本·手动”里选、再把“日本”切到“日本·手动”，两步。简易版一步。

### 4.2 mihomo（Clash Verge Rev、Clash Meta for Android）

- 写法：`日本` = select，`proxies: [日本·自动]`，`include-all-providers: true`，`filter: <宽筛选，原样>`；`日本·自动` = url-test，严筛选，`hidden: true`，`empty-fallback: REJECT`（和完整版相同）；`国外默认` = select，`proxies: [日本, 香港, 韩国, 台湾, 新加坡, 美国, 其他地区]`，`include-all-providers: true`，`filter: <全部节点>`。
- **事实（源码 v1.19.31）**：写明的成员组成一个排在最前面的集合（`adapter/outboundgroup/parser.go:183`），而且不过筛选（`groupbase.go:147`，“compatible provider unneeded filter”）；选择组默认选第一个，记住的选择不在成员里时也回到第一个（`selector.go:103-111`）。所以“日本·自动”永远是第一项、首次导入时选中它。
- **事实（源码）**：`exclude-filter`、`exclude-type` 对全部成员都起作用，包括写明的组名（`groupbase.go:196-224`），所以这两项不能用；筛选用反引号拆成多条时，成员会按筛选的先后重排（`:169-194`），生成器本来就不用反引号。`hidden` 只是给界面看的字段，内核照样能选（`selector.go:73`）。
- **事实（实测）**：小实验 E1：“日本” = [日本·自动, 日本 01, 🇯🇵 Tokyo 02, 日本-美国 03]，选中“日本·自动”；没有韩国节点时“韩国”只剩“韩国·自动”，而它是 REJECT（拒绝，不直连）；重启后选择还在；手选的节点从订阅里消失以后，组回到第一项（`handoff/notes/simple_mihomo/runs/e1.out`）。原型用 2,290 个假节点的实际分组见第八节。
- **推断**：在“国外默认”里手选的单个节点从订阅里消失以后，“国外默认”回到第一项“日本”（同一段代码）。
- **未验证**：Clash Verge Rev、Clash Meta for Android 的界面里，藏起来的“日本·自动”在“日本”的成员里怎么显示、能不能点（内核的接口可以：E1 里把“日本”选成“日本·自动”返回 204）。

### 4.3 Loon

- 写法：`日本 = select,日本·自动,F-JP`（`F-JP` 是现有的宽筛选）；`日本·自动 = url-test,F-JP-AUTO,…`（和完整版相同）；`国外默认 = select,日本,香港,韩国,台湾,新加坡,美国,其他地区,F-ALL`（`F-ALL` 是新加的一条 `[Remote Filter]`：全部节点去掉提示行和占位节点）。
- **事实（官方示例）**：`example.conf` 第 77 行 `PROXY = select,Auto,1,2,3,4,Subs`，一个选择组里混放了策略组（Auto）、节点（1–4）和整份订阅（Subs）；第 67 行 `[Remote Filter]` 的注释是“筛选订阅节点，筛选后的结果可加入到策略组中”。
- **事实（真机，2026-10-20）**：现有的 `香港·手动 = select,F-HK` 这类写法，地区组里是对应地区的节点（`docs/05`“真机记录”第 2 项）。
- **推断**：“组名 + 筛选”混放在一个选择组里可以用——官方示例混放的是组和订阅，没有“组和筛选”一起的例子。要在真机上看“日本”的成员：第一项是“日本·自动”，后面是日本节点。
- Loon 没有隐藏组的写法，“X·自动”会显示出来。

### 4.4 Quantumult X

- 写法（甲）：`static=日本, 日本·自动, server-tag-regex=<宽筛选>`。
- **事实（官方 sample.conf，提交 `af6fb59`）**：第 105–113 行只有两种分开的例子：写明成员的（`static = policy-name-1, Sample-A, Sample-B, Sample-C`），和用正则筛的（`static = policy-name-5, resource-tag-regex=…, server-tag-regex=…`）；**没有写明成员和正则混在一起的例子**。现有配置也从来没有这样混写过。
- **未知**：甲能不能用，要在真机上看“日本”的成员。不行时用乙：`static=日本, 日本·自动, 日本·选节点`，`static=日本·选节点, server-tag-regex=<宽筛选>`。代价是 Quantumult X 上点具体节点要多点一层（回到使用者嫌麻烦的样子），组数多 6 个。
- **另一个隐患，比完整版重**：sample.conf 第 102 行说 `server-tag-regex` 只对 static、available、round-robin 生效，同一文件第 112–113 行又把它写在 dest-hash、url-latency-benchmark 上（`docs/06` 已记）。现有的“X·自动”用 url-latency-benchmark。完整版里默认的“手动优先”= available[手动, 自动]，“自动”不生效时还有手选节点顶着；**简易版默认就是“自动”**，它不生效的话，默认的路就是坏的。所以 Quantumult X 简易版的“X·自动”建议改用 available（第 102 行明确支持正则）：节点挂了照样自动换、只在同地区换，区别是按订阅顺序用第一个能用的，而不是挑最快的。要不要这样做，列在第九节。
- 没有隐藏组的写法，“X·自动”会显示出来。

### 4.5 Stash

- 写法：`日本` = select，`proxies: [日本·自动]`，`include-all: true`，`filter: <宽筛选>`；`国外默认` = select，`proxies: [日本, 香港, …, 其他地区]`，`include-all: true`，`filter: <全部节点去掉提示行和占位节点>`。
- **事实（2026-10-13 下载的官方文档“策略组”页）**：“策略组可以包含另一个策略组”；`select` 的例子里 `proxies` 混放了节点和组（`ss1, ss2, vmess, auto`）；“可以通过 `include-all: true` 引用所有的代理和远程代理集”；“支持 `filter` 字段，通过正则表达式过滤节点”。
- **未知**：`proxies` 和 `include-all` + `filter` 写在同一个组里时，成员顺序怎样、`filter` 会不会也作用在写明的组名上——文档没写。
- **事实（本机核对）**：就算 `filter` 也作用在写明的组名上，各地区的宽筛选正则对自己的“X·自动”这个名字也是匹配的（用 dist 里的正则在 Python 上核对：六个地区都匹配自己的“X·自动”），所以“日本·自动”不会被筛掉。**推断**：Stash 的正则引擎在这些名字上和 Python 结果一样（引擎文档没写，`docs/06` 已记）。
- **风险（推断）**：如果 Stash 把 `include-all` 进来的节点排在写明的成员前面，“日本”首次导入时选中的就是第一个节点，甚至可能是占位节点“日本·无可用节点”，那样走日本的连接全部失败。完整版没有这个风险：它的地区入口默认是“手动优先”，占位节点只在“日本·手动”里。
- **做法（技术选择，请审核方看）**：Stash 简易版的地区组，筛选里去掉本地区的占位节点。组里总有“日本·自动”，不会变空；占位节点留在“日本·自动”里，地区一个节点都没有时照旧连接失败、不直连。这样就算顺序不对，首次选中的也是一个真节点。
- **另一个未知（完整版就有）**：文档说 `include-all` 引用“所有的代理和远程代理集”，没说包不包括策略组。如果包括，“全部节点”这条筛选会把 43 个业务组名和“国外默认”自己也选进来（本机核对：43 个业务组名都能被它选中）；完整版的“其他地区”在同样的前提下也会选进 39 个（`handoff/notes/simple_generator/logs/proto_all_nodes.out`）。真机要看“国外默认”的成员里有没有组名。
- 真机要看：“日本”的第一项是不是“日本·自动”、首次选中的是不是它，后面是不是日本节点。
- `hidden` 不用（文档里没有），“X·自动”会显示出来。

## 五、选“自动”时，节点挂了多久换走

### 5.1 “5 分钟”是什么意思

不是“连接失败 5 分钟以后才切换”，而是“这个组在被使用时，每隔这么久检查一次节点”。节点挂了以后，要等下一次检查才发现，才换。所以最慢差不多一个间隔，平均半个间隔；有的 App 有“连续几次连不上就马上检查”的机制，会更快（见下）。完整版和简易版现在都是 300 秒（`source/project.yaml` 的 `health_check.interval_s`，各端共用）。

### 5.2 sing-box：本机实测（1.14.1；30 秒间隔下 1.12.0、1.14.3 结果相同）

节点都在一次检查之后约 5 秒停掉，接近最坏情况。数字来自 `handoff/notes/simple_singbox/summary.out`（2026-10-21 从保存的事件记录重算过，和第一次整理的结果一致）。

| 情况 | 间隔 300 秒 | 间隔 180 秒 | 间隔 30 秒 |
|---|---|---|---|
| 一直有连接、节点直接拒绝连接 | 295.0 秒（147 个请求失败） | 175 秒（87 个失败） | 25.2 秒 |
| 节点停掉时没在用 | 595.4 秒 | 355.3 秒 | 55.7 秒 |

- **事实（源码）**：sing-box 只在检查之后换节点，连接失败本身不会马上换（`protocol/group/urltest.go:485` 的 `performUpdateCheck`）；上次测成功的时间不满一个间隔的节点，到点时会被跳过（`urltest.go:448`），所以没在用的节点实际约两个间隔才复测一次，表里第二行就是这个原因。
- **事实（源码）**：单次测速超时固定 15 秒（`constant/timeout.go:9` 的 `TCPTimeout`，测速的 HTTP 客户端用它），不看返回码（`common/urltest/urltest.go:124-146`，收到任何响应都算能用）。项目里写的“超时 5 秒”“要求 204”对 sing-box 不起作用（`docs/06` 第 86 行的说法要更正）。
- **事实（源码）**：sing-box 自己的默认间隔就是 3 分钟（`constant/timeout.go` 的 `DefaultURLTestInterval`）。
- SFA 分组页对“日本”或“日本·自动”点测速，会马上重测并换走（1.14.1 本机用同一组函数实测，0.6 秒；1.12 没有验证）。手机换网络时也会马上重测（读源码，没有实测）。

### 5.3 mihomo：本机实测（v1.19.31）

- **事实（源码 + 实测）**：健康检查是**按订阅**做的，每次把订阅里的节点都测一遍（`adapter/provider/healthcheck.go:150-189`）；组上写的测速地址和订阅的相同时，组上的间隔不起作用（`healthcheck.go:70`）。实测：订阅 300 秒、组 30 秒时只测了启动那一次；订阅 30 秒、组 300 秒时每 30 秒测一次（`handoff/notes/simple_mihomo/runs/gi-prov300-group30`、`gi-prov30-group300`）。所以要改成 180 秒，改的是 `proxy-providers` 的 `health-check.interval`（生成器里这两处用的是同一个数）。
- **事实（源码）**：连接失败的错误里有“connection refused”时立刻检查；其他失败在 5 秒（`timeout`）内累计到 `max-failed-times` 才检查（`groupbase.go:265-300`），在“日本·自动”这一层计数，没写时默认是 5。现有配置只给“手动优先”（fallback）写了 3（`generator/emit_mihomo.py:172-173`）；简易版没有 fallback，所以建议给“X·自动”写上 `max-failed-times: 3`。
- 实测（每个请求结束后隔 2 秒再发下一个；节点在一次检查刚结束时出故障，接近最坏；`runs/summary_all.json`）：

| 节点怎么挂的 | 间隔 30 秒 | 间隔 180 秒 | 间隔 300 秒 |
|---|---|---|---|
| 连接被拒（端口关了） | 0.7 秒，0 个请求失败 | 0.3 秒，0 个 | 1.7 秒，0 个 |
| 连得上但不回话 | 40.3 秒，6 个 | 191.5 秒，28 个 | 312.5 秒，45 个 |
| 连上节点但出不去 | 30.3 秒，15 个 | 181.5 秒，91 个 | 302.0 秒，150 个 |
| 不回话，每次 4 个并发，`max-failed-times: 3` | 10.2 秒 | 13.3 秒 | — |

- **推断**：在 mihomo 上，180 秒和 300 秒的差别只在后两种挂法：最坏约 3 分钟对约 5 分钟。“连接被拒”这种和间隔无关，一两秒就换走——这一点 mihomo 比 sing-box 快得多（sing-box 同样的挂法要等到下一次检查，见 5.2）。
- 代价（推断）：每次检查对订阅里每个节点发 2 个很小的请求（配置开了 `unified-delay`，实测确实是 2 个），只在订阅最近被用过时才测（`lazy`）。改 180 秒，检查流量约多 2/3。耗电没有测。

### 5.4 Loon、Quantumult X、Stash

没有能在电脑上运行的内核，只有文档：

- **Loon**：官方示例第 78 行（url-test 那一行的注释）：“默认间隔600s，测速超时时间5s”；本项目写的是 300 秒，测速超时 5 秒（`[General] test-timeout = 5`）。配置里还写了 `switch-node-after-failure-times = 3`，但仓库里没有记下它的依据（从第一版起就有，`generator/emit_loon.py:85`），它是不是“连续失败 3 次就换”、对哪些组生效，**没有核对**。
- **Quantumult X**：sample.conf 第 100 行：url-latency-benchmark 有 `check-interval`，“被请求激活以后才按间隔测”；`alive-checking=true` 时闲着也测。第 97 行：available 在“被使用、而且当前结果不可用”时立即并发测速，闲着不测。
- **Stash**：文档“策略组”页：默认每 600 秒测一次，`lazy: true` 时策略组一段时间没被使用就跳过。连接失败会不会马上重测，文档没写。

### 5.5 改成 3 分钟（180 秒）

- 可以。实测的效果：
  - sing-box：在用时最慢从约 5 分钟缩到约 3 分钟（295 → 175 秒）；没在用时从约 10 分钟缩到约 6 分钟（595 → 355 秒）。180 秒正好是 sing-box 自己的默认值。
  - mihomo：“连得上但不回话”“连上节点但出不去”这两种，最慢从约 5 分钟缩到约 3 分钟（312.5 → 191.5 秒、302.0 → 181.5 秒）；“连接被拒”本来就是一两秒，不受影响。
  - Loon、Quantumult X、Stash：没有内核可测，推断是同一个比例。
- 代价（2026-10-21 使用者问到流量以后补的；**估算，没有实测**）：
  - **流量**：每次检查对每个节点发一两个很小的请求，花的主要是和节点、和测速网站握手的那几 KB，估计一个节点一次约 5–10 KB（Loon、Quantumult X 用的是 http 测速地址，少一次握手，会更少）。这些流量也算在机场的流量里。
  - **测多少个节点**：mihomo 每次把整份订阅的节点都测一遍（`adapter/provider/healthcheck.go:150-189`；订阅最近一个间隔内被用过才测）；其他几端只测正在用的“X·自动”组里那个地区的节点（sing-box 是事实，见 5.2；Loon、Quantumult X、Stash 是推断）；sing-box 上健康的节点实际两个间隔才测一次。
  - **举例**：订阅 50 个节点、Clash 一直开着用：一次检查约 0.25–0.5 MB；300 秒一次每小时约 3–6 MB，180 秒一次每小时约 5–10 MB。只测一个地区 10 个节点的话，大约是它的五分之一。没在用时不测。
  - **电**：手机被唤醒的次数多 2/3（间隔从 300 秒到 180 秒）。耗电没有测。
  - **IP 变得更勤（推断）**：检查越勤，“自动”越容易换到稍快一点的节点（快过 50 毫秒的容差就换），IP 也就变得更勤。
- 好处只在一部分故障上：mihomo 上“连接被拒”这类本来一两秒就换，和间隔无关；间隔影响的是“连得上但不回话”“连上节点但出不去”这类，最慢从约 5 分钟缩到约 3 分钟。
- 还能更短（60–120 秒），代价按比例增加。
- 要定的：只改简易版，还是两版一起改（第九节）。

## 六、“国外默认”能选单个节点以后：DNS 和规则下载会跟着它

- **事实（sing-box，配置）**：境外 DNS（`dns-foreign`，1.1.1.1 DoH）和规则集下载都经“国外默认”出去（`dist/sing-box/sing-box-1.14.json`：`dns.servers` 里 `dns-foreign` 的 `detour` 是“国外默认”；`http_clients` 的 `detour` 也是；1.12 版的 `download_detour` 同样）。
- **事实（sing-box，本机实测）**：“国外默认”选中一个已经停掉的节点时，一个没被任何规则认出的域名，为判断 IP 规则要先用 `dns-foreign` 解析，解析失败，连接直接被关掉；“国外默认”是正常节点时同一个请求成功（`handoff/notes/simple_singbox/runs/dnsdep-1.14.1`、`dnsdep-1.12.0` 的 `sing-box.log`）。
- **推断**：所以在 sing-box 上，“国外默认”选了一个挂掉的单个节点，不只是境外网站打不开：没被规则认出的网站都会打不开，包括不在国内域名集合里的国内网站；规则集也更新不了。这和“国内网站不能变慢”冲突。真实的国内网站没有测。
- **事实（mihomo，配置和源码）**：`respect-rules: true`（`dist/mihomo/mihomo-profile.yaml:31`），境外 DNS（1.1.1.1、8.8.8.8 的 DoH）和 `nameserver-policy` 里用境外 DoH 的条目，都按规则连，最后落到 `MATCH,国外默认`；`direct-nameserver-follow-policy: true`（`:785`）让直连时也按这份策略解析；geodata 更新也按规则走（下载地址命中境外集合，经“国外默认”）。订阅下载写的是 `proxy: DIRECT`，不受影响。
- **事实（mihomo，本机实测）**：“国外默认”选中一个停掉的节点时：没被规则认出的域名 502；不在 geosite:cn、但境外 DNS 会答国内地址的网站也 502；geosite:cn 里的国内网站照常直连；走 OpenAI 组（它的节点正常）的 TCP 正常，但 UDP 因为解析不了被丢掉；手动切成直连、域名又在境外 DNS 策略里的组 502；设备问 `www.msftconnecttest.com`、`www.msftncsi.com`、`captive.apple.com` 得到 SERVFAIL（`handoff/notes/simple_mihomo/runs/e3v2.out`）。
- **推断（mihomo）**：开着虚拟网卡时，系统的联网检测会失败，Windows、macOS、iOS 可能提示“无 Internet”。没有在设备上验证。
- Loon、Quantumult X、Stash：DNS 用的是国内 DNS、直接发出，不经“国外默认”，不受影响。没被规则认出的境外网站走“国外默认”，会一起连不上——这是选单个节点的本意。严格版里清单以外的国内网站也走“国外默认”，也会连不上（严格版本来就让它们走代理）。这三端下载远程规则（以及 Stash 首次用到 GEOSITE 时从 github.com 下载数据）走哪条路，文档没写，没有核对。
- **不只“国外默认”**：“国外默认”选“日本”、而“日本”里点了一个挂掉的节点，效果一样。所以只靠“国外默认里不放单个节点”解决不了。完整版里没有这么容易碰到：地区默认是“手动优先”（mihomo、Loon、Quantumult X、Stash）或“自动”（sing-box），手选的节点挂了还有自动兜底。

要使用者选（第九节）：

1. **维持**：DNS 和规则下载照旧跟着“国外默认”，说明里提醒“国外默认尽量选地区，地区里尽量用自动”。
2. **DNS 和规则下载另走一个内部的自动组**：在六个地区的节点（严筛选）里自动测速，只给 DNS 和规则下载用，不影响网页和 App 的流量走哪里。不受手选影响。代价：多一个组（mihomo 上藏起来，sing-box 上看得见）和一张图标；DNS 的出口地区可能和“国外默认”的不一样——推断影响很小：假地址模式下，境外网站的连接本来就是把域名交给节点，这次解析主要用来判断该不该走 IP 规则（mihomo 上还有本机解析的 UDP，见上）。
   - 写法的依据：mihomo 的境外 DNS 可以写成 `https://1.1.1.1/dns-query#<组名>`（`config/config.go:1212-1222` 解析 `#` 后面的组名；这样写以后 `respect-rules` 对它不再生效）。本机实测用“日本·自动”代替这个组：DNS 那几项都恢复了，没被认出的境外网站仍然失败（连接本身还是走“国外默认”）（`runs/e3c-dnsvia.out`）。sing-box 改 `dns-foreign` 和 `http_clients` 的 `detour`。mihomo 的 geodata 下载要为下载地址另加一条规则。
   - 为什么不直接用“日本·自动”：没有日本节点、或者日本节点全挂了时，DNS 就全断了。在六个地区里挑更稳。
   - 不采用的写法：fallback[国外默认, 各地区·自动]。实测启动后约 10 秒内会拒绝走 OpenAI 的请求（启动时的竞态，`runs/e3d-dnsfallback.out`）。
3. **“国外默认”只放地区、不放单个节点**：和使用者第 4 条要求不符，而且像上面说的，也解决不了“地区里点了挂掉的节点”的情况。

我的建议是 2，理由：它把“使用者手选的节点挂了”的影响限制在使用者自己选的那些流量上。

## 十一、已知代价

- 点了具体节点：挂了不会自动换（五端都是）。要自动换就选“X·自动”。
- 选“自动”时 IP 会自己变：节点挂了会换；测速快慢差超过容差（50 毫秒）也可能换。在意 IP 的服务固定一个节点。
- 地区组里直接列出节点，成员列表变长。
- 从完整版换到简易版：完整版“X·手动”里选的节点，在简易版里用不上（组名不同），要在“X”里重选一次。两份配置在同一个 App 里来回切换时，App 记住的选择是按配置分开存、还是按组名共用，不知道（真机看）。
- sing-box：单次测速超时固定 15 秒、不看返回码；1.12.0 遇到“接受连接但不回话”的 SOCKS 节点时，自动测速组会卡住不再换（本机实测 `hang-112`；Shadowsocks、VMess、Trojan 没有这个问题；真实机场常用的其他协议没有测）。

## 十三、顺带发现：完整版的一个小问题（mihomo）

本机实测（`handoff/notes/simple_mihomo/runs/e5.out`）：完整版启动 4 次，有 2 次在启动后的约 10 秒里，“日本·自动”是 REJECT，“日本·手动优先”把两个成员都记成不可用，到第 12 秒还是这样，要等下一次检查（最多一个间隔）。这段时间“手动优先”仍然用“日本·手动”里选的节点，所以平时的路不受影响；受影响的是：如果启动时手选的节点正好是坏的，自动兜底要等到下一次检查才起作用。原因（读源码推断）：订阅是在后台并发加载的（`hub/executor/executor.go:340-350`），“带健康检查、成员里又有组”的组可能在订阅读进来以前就测了一次。简易版没有这种组，启动 4 次都正常。这一条先记在这里，出下一版时写进 `docs/06`，要不要改另说。
